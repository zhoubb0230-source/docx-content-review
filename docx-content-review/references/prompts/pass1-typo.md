# Pass 1 支线 · 错别字裁定 prompt 模板（A1）

**任务已经被脚本切成二选一**：候选由 `typo_scan.py scan` 用错词表与术语表
确定性地找出来了，你只回答——**这两个写法，此处该用哪一个。**

## 为什么错别字不能靠主审查顺带发现

spec §9.7 的三条理由，写在这里是为了让人别把它并回主通道：

1. **模型对错别字有鲁棒性，这恰是缺陷。** 读到「布署」「帐号」会自动理解成正确词，
   注意力不会停留——它在做语义理解，不是逐字比对。
2. **配额挤占。** 一片 20 页可能有 20–40 个错别字，`max_issues_per_chunk: 20`
   瞬间打满，且截断按 severity 排序，A1 会被 Critical 级挤掉。
3. **重要性排挤。** 模型倾向报告"看起来更重要"的问题，错别字最不起眼。

把任务退化成二选一之后，中等模型的准确率显著高于自主发现，
且单条输出只有一个字母，一次调用可处理 50 个候选，成本极低。

## 输入

`work/typos/typos-<chunk>.json`，每批 ≤50 个候选（`batches[i].items`）。
每个候选带 `pid` / `wrong`（原文写法）/ `right`（候选正字）/ `context`（±6 字上下文）。

## prompt 形式

```
下面每行给出一处上下文，以及其中一个词的两种写法。
判断在**这个上下文里**应当用哪一种。

A = 用原写法（原文没错）
B = 用候选写法（原文写错了）
C = 两个都不对

只看这个词写得对不对，不要评价句子的其他部分，不要提出任何别的修改。
遇到人名、地名、产品名、专有名词、引文，一律答 A。

1. 上下文「系统布署完成后」 —— 原写法：布署 / 候选写法：部署
2. 上下文「在野外搭起帐篷」 —— 原写法：帐篷 / 候选写法：账篷
3. …

输出：每行 `序号 答案`，例如 `1 B`。不要任何其他文字。
```

## 输出与写回

逐行追加到 `work/typos/typos-<chunk>.verdicts.jsonl`，
**必须回填候选的三个定位字段**，否则 `merge` 对不上：

```json
{"pid":"p-000412","wrong":"布署","context":"系统布署完成后","verdict":"B"}
```

`verdict` 是封闭枚举 `A` / `B` / `C`。

## 只有 B 会被采纳

`typo_scan.py merge` **只采纳 `B`**，`A` 与 `C` 一律丢弃：

- `A` = 原文没错，本来就不该报；
- `C` = 两个写法都不对。此时正确写法是什么并不确定，
  按"不确定即无问题"丢弃——不要试图让模型给第三种写法。

## 白名单陷阱

候选是靠字符串匹配生成的，必然带这类噪音：

| 上下文 | 候选 | 正确答案 |
|---|---|---|
| 在野外搭起**帐篷** | 帐篷 → 账篷 | **A**（帐篷是正确写法） |
| **渡过**湍急的河面 | 渡过 → 度过 | **A**（过水面用渡） |
| 度过难关 | 度过 → 渡过 | 不会成为候选（表里只登记「渡过难关→度过难关」） |
| 引文《XX 法》第五条原文里的写法 | 任意 | **A**（N10：引文逐字保留） |

答对这些噪音正是本次调用的主要价值。`assets/dict/typo-whitelist.txt`
已经拦掉了一部分，但词表拦不住上下文相关的情形——那是你的职责。

## 调用约束

- 温度 0；一次 ≤50 个候选（`batch_size`）。
- 一次调用只做这一件事，**不要和 Pass 1 的审查或事实抽取合并**。
- 候选有独立配额 `max_typos_per_chunk`（默认 100），不占用主审查的 20 条。
- 不要输出理由。理由越长越容易自我说服，且这里根本不需要理由。

## 之后会发生什么（不需要你做）

`merge` 把 `B` 转成 `category: A1` 的条目，`suggested_text` 由脚本做字符串替换生成
（不是你写的），随后照常过闸门② `verify_span.py`（A1 要求长度差 ≤2 且差异字符 ≤3）
与闸门③ `filter_neverflag.py`，并入 Pass 2 的待复核集。
