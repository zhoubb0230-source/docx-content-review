# Pass 2 · 二次独立复核 prompt 模板（盲测 A/B）

**这是四道闸门里唯一一道靠模型的闸门，它的设计要点全在"不给锚点"上。**

## 为什么是盲测 A/B

把 `category: A2` 连同原文一起交给模型，等于告诉它"这里有个错，你确认一下"——
这是锚定，确认率会被显著抬高，复核就退化成了橡皮图章。
但反过来问"这段文字是否存在需要修改的问题"又是开放题，中等模型会持续发现新问题。

两难的解法是盲测 A/B：**不告诉模型问题类别，也不告诉它哪一个是原文。**
这同时达成三件事——消除锚定、保持封闭选择题、并且顺带验证了"建议确实优于原文"。

## 调用约束

- **位置随机化由 `verify_pass2.py build` 完成，不要自己拼 A/B。**
  它按 manifest 的 `ab_seed` 逐条派生位置（可复现），并把「原文在哪一侧」
  单独写进 `.key.json`——**那个文件不要读，更不要带进调用**。
  判定表要求"选中原文所在项才算通过"，拼装者若同时应用判定表，盲测只剩名义。
- **上下文里所有待判跨度都已被脚本挡成 `【　】`。** 这不是脱敏，是防泄题：
  上下文那一段正是原文所在的段落，原样给出等于把答案写在题面上；
  且一批 10 组的上下文彼此重叠，只挡本条根本不够（实测 15 条里 14 条会漏）。
  **看到 `【　】` 是正常的，不要因此认为上下文不完整而去猜被挡掉的内容。**
- **一批一个文件，一个子 Agent 只读自己那一批。** `build` 把待复核集按
  `verify_batch_size`（默认 10 组）拆成 `work/verify/pass2-<排列>.vNN.json`，
  各批之间没有任何依赖——闸门④天然可以并行。合并文件 `pass2-<排列>.json` 只留作备查，
  **不要拿它发起调用**：几百条待复核项整份进上下文之后，此后每一轮工具往返
  都要把它重算一遍。
- 温度 0。不要在 prompt 中出现类别名、规则号、"错误""问题""修改"之外的任何提示。

## 形式一：有 `suggested_text` 的条目（A 类、L25/L26）

```
以下每组给出两种表述，判断哪一种存在明确的语言错误。

第 1 组
A. {{文本一}}
B. {{文本二}}
上下文（仅供理解，不要评价上下文本身）：{{前后各一段}}

第 2 组
…

对每一组只回答一个词：A / B / 两者都没有 / 两者都有
输出格式：每行 `组号 答案`，例如 `1 A`。不要任何其他文字。
```

判定表（`{{文本一}}` `{{文本二}}` 由程序随机分配为原文与建议）：

| 模型回答 | 结果 | 理由 |
|---|---|---|
| 选中**原文**所在项 | **通过** | 模型独立认出了原文有错，且认为建议更好 |
| 选中**建议**所在项 | 淘汰 | 建议反而更差 |
| 两者都没有 | 淘汰 | 模型认为原文没问题 |
| 两者都有 | 淘汰 | 模型未能区分，视为不可靠 |

## 形式二：无 `suggested_text` 的条目（B 类）

无法做 A/B，退化为封闭单问：

```
下面这段文字中，「{{片段}}」处的{{指代/歧义/结构}}是否会导致读者产生两种以上理解？

上下文：{{前后各一段}}

只回答：YES / NO / UNSURE
```

**UNSURE 一律按 NO 处理**（即淘汰）。这是本技能接受召回损失换取精确率的地方，
不要为了"多留一些"而把 UNSURE 当 YES。

## 触发范围（受 strictness 控制）

**「启用」与「复核」是两件事。** 不复核的类别（C、P）不会消失，
它们照常留在 `issues-verified.jsonl` 里、按各自的 action 决定去向，
只是 `verify.method` 标成 `not_reviewed`。把两者当成一件事，
下游看到的就是"这些类别根本没产出过"。

| strictness | 启用类别（保留范围） | 二次复核范围 |
|---|---|---|
| `conservative` | A | 全部 A 类 |
| `balanced`（默认） | A + B | 全部 A + B 类 |
| `thorough` | A + B + C | A + B（**C 类跳过复核，且只进报告**） |

## 结果写回

你只需按行写裁定，**判定表由 `verify_pass2.py merge` 执行**：

```json
{"id":"3b1089d0a7737959","answer":"A"}
```

写到**本批自己的文件** `work/verify/pass2-<排列>.vNN.verdicts.jsonl`
（与 payload 同名，后缀换成 `.verdicts.jsonl`），本批全部答完一次性写入。
并行时**各写各的**：多个子 Agent 往同一个文件里 append，中断处会互相截断，
而 JSONL 的坏行是静默丢失的。`merge` 会把所有分批文件一起读进来。

`answer` 对 A/B 组是 `A` / `B` / `两者都没有` / `两者都有`；对封闭单问是
`YES` / `NO` / `UNSURE`。**无法解析的回答、以及漏答的条目，一律按淘汰处理**——
不要为了凑齐而猜，漏答比乱答代价小。

`merge` 会在原记录上补出 `{"verify":{"result":…,"method":…,"position":…}}`，
`position` 记录原文当时在哪一侧，供偏好分析使用。

## 不复核哪些（**不复核 ≠ 丢弃**，这几类照常留在 `issues-verified.jsonl`）

- **C 类**：不生成修订也不生成批注，复核没有意义。动作恒为 `report_only`。
- **P 类（范式）**：它的裁定本来就是封闭题，且当时**规则包的正反例在上下文里**。
  Pass 2 没有规则包，再问一遍只会得到信息更少的答案。
- **建议已被闸门②清空的 A 类**：没有可对照的两项，它已经是批注。

## 位置偏好怎么测（M2 验收项）

`build --arrangement mirror` 再复核一轮，`verify_pass2.py consistency` 给出
两种排列下的判定一致率。**要求 ≥90%；低于此说明模型答的是"哪一侧"而不是
"哪一个有错"，此时要换 prompt，不能靠调阈值补救。** 常规运行不需要跑镜像排列。

## 落笔门槛（固定，不可放宽）

只有 **A 类 + 有 suggested_text + 通过分类编辑距离 + 二次复核 pass** 才生成修订。
等价于 `apply_threshold = conservative`。用户要求放宽报告门槛可以照办，
但**落笔门槛不放**。
