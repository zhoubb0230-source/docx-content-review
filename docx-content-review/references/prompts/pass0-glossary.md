# Pass 0 · 术语确认 prompt 模板

**不要让模型通读全文来抽术语。** `glossary_scan.py` 已用脚本筛出候选，
并把每个候选所在段落及其前后各一段打包成 batch。你只需对每个 batch 发起一次调用。

2000 页文档的候选术语通常在 200–500 个量级，聚合后约 10 次调用即可完成 ——
相比全文扫描（约 60 次）节省约 50 分钟。

漏掉低频术语是可接受的：低频术语很少产生跨章节冲突，用户也可通过权威术语表补充。

## 调用形式

温度 0。占位符 `{{ITEMS}}` 填 batch 中的候选项（`term` + `sources` + `context`）。

```
下面是从一份技术文档中提取出的候选术语，以及它们出现的上下文。
对每一个候选，判断它是不是这份文档中有确定含义的术语，如果是，给出定义与别名。

{{ITEMS}}

每行输出一条 JSON，不要代码围栏、不要说明文字：
{"term":"边缘节点","is_term":true,"definition":"部署在网络边缘、承担就近计算任务的节点","variants":["边缘结点","EN"],"scope":"global"}

规则：
- `definition` 只能来自上下文中文档自己的表述，**不要用你的常识补充**。
  文档没有定义的，`definition` 留空字符串。
- `variants` 只填**在给出的上下文里实际出现过**的其他写法。没有就给空数组。
- 判断不是术语（普通词组、临时搭配、句子片段）时输出 `{"term":"…","is_term":false}`。
- 不要新增候选之外的术语。
```

## 已有权威术语表时

已在 `authoritative` 层登记的术语**跳过定义推断**，只记录出现位置与实际写法 ——
用户的表是权威，不需要模型重新定义，这也顺带降低 token 消耗。
`glossary_scan.py` 会在 batch 中标注哪些候选属于此类。

## 结果写回

汇总为 `work/glossary-extracted.json`：

```json
{"entries":[{"term":"边缘节点","definition":"…","variants":["边缘结点"],"scope":"global"}]}
```

随后由 `import_glossary.py` 与外部表在**合并阶段**汇合。
**不要在抽取阶段就把三层混在一起** —— 分层是"补充术语表只需重跑 Pass 3/4"的前提。

## 概念族只作建议，不作判据

脚本会给形近的候选打上 `cluster_id`，但一律标记 `cluster_confirmed: false`。
**未确认的概念族不触发任何规则**，只输出到报告的「待确认概念族」一节供人工核对。

自动聚类本身是高误报源：「AI助手 / 智能助手 / 研发助手 / 智能体」可能是一个概念的多种写法，
也可能是几个不同的东西。聚错了会让 L04/L05 批量误报。
正确的路径是：**第一轮跑出建议 → 人工确认 → 第二轮才产生判定力**。
不要试图让系统自动获得判定力。
