### 2026-08-19 主 Agent 的上下文里，一半是同一条路径（ADR-046）

修完死循环后重跑，主 Agent 上下文仍偏高。照主流程在同一份 800 页语料上回放并逐条计量：
**97,680 字符 / 68 次工具往返，其中 49% 是 run_dir 绝对路径的重复**——
每单元两条绝对路径，`claim next` 的 stdout 里一次、转给子 Agent 时再一次。

`claim next` 的单元视图砍到 `{unit, prompt 文件名}`，目录顶层说一次（`output` 冗余：
prompt 抬头本来就写着输出路径）；`init` 不再吐 artifacts；两个 `--all` 类脚本
只列非零的片。**97,680 → 53,121 字符（降 45%）**，一条 `claim next` 从 985 → 267。

第二个杠杆是配置：`--count 4` 才是真正的上限而不是预算，默认值按 ≤64k 窗口定的。
`6/120000` → 14 次 claim / 10 个子 Agent / 33k 字符。**不改默认值**，按窗口自行调；
取舍是主 Agent 上下文换子 Agent 的每轮重算，写进了 SKILL.md 与配置注释。

回归加了数字断言（第 26 节）：一条 `claim next` 里 run_dir 只准出现一次、
单元视图不超过 120 字符——这类退化不会让任何断言变红，只会让上下文悄悄涨回去。
现在 236 项。

### 2026-08-19 第五轮压测：第一波根本走不出去（ADR-043/044/045）

用户在 OpenCode 与 Deepseek 上各跑一次 800 页（211,573 字符）的文档，
**十几个小时都停在第一波**，日志里是上下文溢出与二十多条排队中的子 Agent 消息，
平台统计显示智能体在约 90 分钟处终止。

在同规模的仿真语料（211,586 字符 / 4057 段 / 165 表 / 30 片）上复现并定位：

1. **review 阶段的完成标记指向闸门产物**（ADR-043）。子 Agent 写的是
   `issues-<片>.raw.jsonl`，完成判定看的却是闸门②③才产出的 `issues-<片>.jsonl`，
   而闸门是整波之后的收口。于是 `done` 恒 0、`pending` 恒不降、
   每波结束的 `claim reclaim` 把刚做完的单元一并放掉，下一轮又领到同样的单元——
   **`exhausted` 永远不为真，第一波永远出不去**。这就是"卡在第一步"与
   "二十多条排队的子 Agent"的全部来源；主 Agent 的上下文溢出是它的后果，不是原因。
2. **`state.py stats` 恒定输出 0/0/0**（ADR-044）。`init` 写下的全零 stats 占位
   让"缺失才重建"这条分支永远不进。而 SKILL.md 的续跑路径正是叫人去看 stats——
   接手的会话看到的永远是"什么都没做"。已改为每次重扫，并增加每一波的进度。
3. **闸门摘要的 `dropped` 恒为 0**（ADR-045）。键名前缀写反了。压测里 233 条候选
   被长度闸门全数丢弃，摘要仍报 `dropped: 0`——"模型没查出东西"与
   "查出来的全被丢了"长得一模一样，而这两件事的处置完全相反。

回归补了第 27 节：**照着 SKILL.md 第 4 步的顺序把波内循环跑一遍**
（claim next → 写 output → claim reclaim → 下一轮，**中途不跑闸门**），
四波各配"完成标记必须等于子 Agent 产物"的通用守卫与一条负向对照。
这正是 CLAUDE.md 早就写下、却一直没有落实的那一条：
**没有一项测试是照着 SKILL.md 的主流程从头跑一遍的**——221 项全绿，主流程第一步就断。
现在 235 项。

**顺带确认了后面没有第二堵墙**：修完之后在这份 800 页语料上把整条主流程跑到交付物
（Pass 1 → 四道闸门 → Pass 3/4 → 回写 → 四项校验 → 打包 → 报告），
全部确定性脚本合计不到 5 秒，`detect_conflicts` 0.18 秒。
**墙上时间全部在模型出字上**，这一点与 ADR-042 的结论一致。

**由此新增 SKILL.md「一个会话跑不完怎么办」一节**：这类文档装不进一个有墙上时间
上限的会话，要按"分几次跑完"来安排，并给出被平台杀掉之后的接手序列
（`--resume reuse` → `lease takeover` → 四个阶段各 `claim reclaim`（不带 `--session`）
→ `state.py stats`）。该序列已实测：6 个已完成单元一个不丢，派活从第 7 个继续。

### 2026-08-18 第四轮压测：工具调用的开销是模型自己的出字时间（ADR-042）

近 60 分钟第一波没跑完，平台统计 LLM 33 分钟 / 工具调用 24 分钟 / 60 token/s。

- **24 分钟不是脚本慢**：实测脚本在 800 页语料上是 76–183 毫秒，整轮加起来不到一分钟。
  这是「每次调用的固定开销 × 次数」——模型要先把工具调用「说出口」（一两秒），
  再加拉起子 Agent 与往返。
- **33 + 24 ≈ 墙上时间，说明子 Agent 是串行执行的**，`parallelism` 无效。
- 对策：`claim next --count N` 按上下文预算**成组派活**；错别字候选**跨分片攒批**。
- 顺带修掉一个会导致无限重派的缺陷：零问题的分片产出的是**空 JSONL**，
  而 `product_ok` 把空文件一律判为未完成。

### 2026-08-18 第一次真实压测：成本在轮次与上下文，不在脚本（ADR-039）

801 页、211,573 字符的文档跑了 4 小时还停在第 4 步；31 片里第一轮的 6 片都没做完，
子 Agent 的上下文已到 175k。脚本侧全程只占几十秒——**瓶颈全在流程形状上**：

1. **片数被虚高的 token 系数抬了两倍。** `_estimate` 本来就把 CJK 逐字记 1 token
   （真实约 1 token / 1.4–1.7 字），`token_fallback_ratio` 又乘 1.6。
   加上无条件扣掉 4000 术语摘要预算（`term_rules` 默认关，根本没有摘要）
   与切点比例 0.5，同一份 800 页正文实测 37 片 → 改后 19 片。
2. **子 Agent 连做多片，上下文平方级累积。** prompt 契约里的「每次调用无状态」
   对 API 调用成立，但执行载体是一个持续对话的子 Agent。改为**一片一个、做完即退**。
3. **每片 20+ 轮工具往返里只有 3 轮在做审查。** 其余是每次调用前后的 claim 续期、
   六个闸门脚本各一轮、以及「逐行写入」诱导出的逐行落盘。压到 3 轮。
4. **闸门④与 Pass 4 是下一堵墙**：都在主 Agent 里串行，且要把整份候选读进上下文。
   两步都改成按批分文件、子 Agent 并行；Pass 4 为此新增 `adjudicate_pass4.py`。

顺带修掉两个存量缺陷：**重新分片不清旧产物会静默跳片**（「文件存在性即状态」+
只删 `chunk-*.txt`），**`load_config` 不读 run 的配置快照**（改配置后半生效且不报错）。
两条都配了负向对照（回归第 20 节）。

**没做的**：3000 页压测本身；`parallelism` 的经验上限仍是 5/建议 8，未由压测确定。

### 2026-08-12 第二轮通读：输入不是白纸时会怎样（ADR-038）

前一轮盯的是"通道断没断"，这一轮盯的是**输入本身带着内容**——
六份 fixture 里没有一份带既有批注或既有修订，这条路径从没被走过。

1. **审查一份已经带批注的文档，会把原有批注全部抹掉，而四项校验全绿。**
   `apply_comments` 另起一份 comments.xml 整份写入，编号又从 1 开始，
   与正文里既有的 `commentRangeStart id=1` 撞号——旧锚点转而指向新批注。
   第四项校验查的是"配对齐全 + id 已声明"，撞号之后**每一条都成立**。
   这与 ADR-008、ADR-031 是同一类错误的第三次出现：
   **校验描述了结构，没有描述"用户的东西还在不在"。**
   已改为追加写入 + 编号避让 + 增强层降级时恢复原内容而非删文件；
   `unpack` 存 `comments.baseline.xml`，校验新增"原有批注一条不少、一字不变"。
   新增 fixture `existing-comments.docx`。
2. **截断去重键漏掉原文**：`(pid, category)` 把同段同类的不同问题折叠成一条，
   实测 cap=3 只保留 2 条——配额没用满还丢了真问题。
3. **未准入的冲突候选被记成「批注」**：实测 28 条。而 SKILL.md 要求 Agent
   正是照着这份报告向用户口头汇报，等于虚报了文档里并不存在的批注数。

### 2026-08-12 定位歧义守卫；术语规范化改为整段替换（ADR-036）

`ooxml.locate_span` 取的是**首个**匹配，而问题记录里只有 pid 与 original_text、
没有偏移量。`logic-injection.docx` 里就有现成的一段——「本期指标目标为 200ms，
实测值为 1200ms。」——把「200ms」改掉，**改中的是目标值还是实测值取决于 find**。

改为：唯一则落笔；带 `all_occurrences` 则逐处全换；其余不落笔，记为失败并附
出现次数，照常出普通批注（不静默消失）。批注锚点同理，但**判定放在 plan 里、
依据原始段落文本**——第一版放在 apply 阶段，回归立刻抓到：那时段落已被修订改过，
判出来的结论与计划不一致。

顺带修掉一个存量缺陷：**L25/L26 原先只换首处**，剩下的原样留着，
文档会停在半规范化状态。若只加守卫不处理这条，它会从"换一半"退化成"一处也不换"。

错别字通道的候选窗口也从固定 ±6 改为撑到段内唯一——重复句里的固定窗口
产出的候选注定落不了笔，白白消耗一次裁定调用。

### 2026-08-12 闸门③ 的位置类规则改为按区域判定（ADR-035）

N9/N10/N12 讲的都是"这个**区域**内的内容不审查"，实现却是"段落里出现该特征就
整段免检"。技术文档里一句话带一条 URL、一个 `cpu_usage=80%`、一句
"按照本办法第五条执行"都极常见——按整段判，含这些特征的段落里所有语病
都被静默吞掉。这是 ADR-030 给 N7 定下那条判据后**没有推广到的另外三条**。

先补语料再动规则：`tests/fixtures/neverflag-traps.json`（21 条，正 13 / 反 8）+
`filter_neverflag.py --traps` 自检。**语料第一次跑就撞出一个存量漏洞**——
`never-flag.md` 自己举的反例「合同第 3.2 条约定：…十五个工作日内交付。」，
旧条号正则不接受小数分节，这条文档里写着的保护从来没有生效过。

**这四条一条都没被原有 110 项覆盖到**，原因值得记：回归第 9 节测到
`issues-0001.patterns.jsonl` 为止就停了，从没跨过 `verify_pass2`；
租约的单元行为测过（第 6 节令牌栅栏），但**没有一项测试是"照着 SKILL.md
的主流程从头跑一遍"**。新增第 14、15 节共 11 项，四条各配负向对照并已验证会失败。

### 2026-08-11 术语类规则整组默认关闭（ADR-033）

按用户要求「术语的检查先跳过」，L01–L05 与 L25/L26 共七条由 `logic.term_rules`

### 2026-08-10 批注可读性与锚定精度（ADR-032）

用户看过上一轮的产出后又提两条，都已修：

1. **抬头去套话**：修订理由批注不再写「— 已在此处标为修订，请确认后接受或拒绝」，
   冲突批注不再写「— <规则通用描述>」。抬头只留类别标签，
   判据是"这句话有没有增加信息"。写长了评审人就不看了。
2. **锚定精确到字符**：ADR-031 里"边界对齐到 run、多圈一点无妨"的判断在真实文档上
   是错的——run 合并后一整段常常只剩一只 run，"多一点"等于"整段"。
   改为先把锚点切成独立 run（`ooxml.isolate_span`）。
   这不违反 D9：文本逐字不变、rPr 深拷贝，与修订回写同一套机制、同一套负向对照。

### 2026-08-10 第二轮真实运行后的修正（ADR-031）

用户实跑后报了两个现场问题，都出在回写的最后一厘米——判定全对，交付物读不出来：

1. **修订处没有批注，看不出为什么改**。原实现认为"已落笔为修订就不必再批注"，
   但修订标记只显示改成了什么。现在每处修订同时写一条 `kind: revision` 的批注，
   正文只答"为什么改"，并按 `del_id`/`ins_id` 精确锚在这处改动上
   （拒绝视图圈住的正是原文，接受视图正是建议）。
   顺带修掉一个静默丢失：计划了修订但定位失败的条目原先既无修订也无批注。
2. **批注只选中前面几行**。根因是把"定位用的 run 集合"当成了"锚定用的 run 集合"：
   含 `w:br`/`w:tab`/图形的 run 与既有修订被排除在范围外，段落末尾有软换行时
   范围就止于换行之前，整段在一个含 `w:br` 的 run 里时范围直接塌成零长度。
   范围边界改取 `w:p` 的直接子节点，定位不到即退回整段；
   冲突批注锚点的 `[:40]` 硬截断同时去掉。
3. **校验补齐**：第四项原来只查 Start/End 配对，上述三种现场全都能过。
   现在加查"范围内有正文"与"范围覆盖完整锚点"，并配两条负向对照。

**第六轮：术语表的压制方向（`pass0-glossary`）**

术语表有个别处没有的性质：**它是唯一一个用来压制发现的输入**（N7、L05）。

- **未在"含 100 个已知错别字"的真实语料上测过召回率**（SPEC §15.1 M8 要求 ≥85%）。
  当前 fixture 只植入 8 处，够验证链路，不够标定。

- 未登录词检测按 ADR-023 不做。若将来要做，需先决定是否内置 5–10 万词表
  （数 MB + 词表来源与分发许可），这是个待用户拍板的取舍。

### 3b. M9 范式规则包等用户补真实正反例

`assets/patterns/builtin-examples.yaml` 里的两条（风险条目、接口描述）是**示例**，
用来给出规则的写法与粒度。真实范式是场景特定的，需要用户提供正例/反例后才能填。
在拿到真实规则包并人工核对误报率之前，`severity_cap` 不要放宽（SPEC §15.1 M9）。

都只在 Linux 上跑过。

## 未决问题

- **L29–L32 的误报率没有基线。** SPEC 要求"首轮跑完应人工核对其误报率，再决定是否提升
  其地位"。目前默认 `coverage_rules_to_comment: false`（只进报告），在拿到基线前不要改。
- **XSD 校验是已知缺口**（ADR-007）。若要补齐，需决定是否内置 ECMA-376 schema
  （数 MB + 分发许可问题）。
- **`report.py` 的「术语表覆盖率」一节按 `preferred` 是否出现在全文判定**，
  对有 scope 限定的术语会偏乐观。真实语料上看过再决定要不要按 scope 细化。
- **P 类的误报率没有基线。** 与 L29–L32 同样的处境：`severity_cap: Medium`
  是保守缺省，拿到真实规则包的基线前不要放宽，也不要给 P 类开修订口子。
- **同一实体关系在多个段落各出现一次时，L04 会产出多条候选。** 实测基线里
  「边沿节点/边缘结点」出了 2 条。不是误报，但评审人会看到重复条目。
  跨片、跨段的候选去重是 Pass 3 的已知薄弱点，等真实语料上看过再决定合并策略。
- **范式规则只看单个段落。** "风险表述分散在连续三段里"会被判成缺要件。
  规则该用 `min_chars` 或更严的 `paragraph_regex` 把这类段落排除；
  是否要支持跨段落范式，等真实语料上遇到了再定。
