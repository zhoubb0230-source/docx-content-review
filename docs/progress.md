### 2026-08-12 全量通读发现四条断链（ADR-034）

从设计到实现通读了一遍，四条缺陷都指向同一个形状——
**为 A/B 类定的判据被无差别套到了所有通道上**：

1. **P 类整条通道是断的**。`verify_pass2.collect()` 拿"复核范围"当"保留范围"用，
   而 `issues-verified.jsonl` 是下游四处的唯一入口——范式支线过完两道闸门后原地蒸发，
   需求 5 在交付物和报告里都看不见（报告 §6 还会显示"要件缺失 0"，读起来像查过了）。
   顺带 `thorough` 与 `balanced` 完全等价，C 类连报告都进不去。
   已拆成 `REVIEW_SCOPE` / `KEEP_SCOPE` 两张表。
2. **`max_span_chars: 120` 误杀 P 类**。P 类的跨度按设计就是整段，
   实测 155 字即被丢，而真实风险条目/接口描述普遍超 120 字。
   已新增 `pattern_review.max_span_chars`（默认不限），**不动 A/B 类的 120**。
3. **闸门②无条件重算 action**，把上游的 `report_only` 升成 `comment`——
   规则包里的 `action: report_only` 与"只缺可选要件不打扰评审人"都是空头支票。
4. **主流程从来没取过租约**。`SKILL.md` 没有一处 `lease acquire`，
   但第 6/7/8 步都带 `--session` 调会 `lease_verify` 的脚本。照文档跑，
   Pass 3 会以 exit 9 终止，而那句话说的是"已被另一个会话接管"——与实情相反。
   已补 init 的 `lease`/`next` 返回、SKILL.md 第 0 步、以及 exit 9 的分诊指引。

### 2026-08-12 闸门③ 的位置类规则改为按区域判定（ADR-035）

### 2026-08-10 批注可读性与锚定精度（ADR-032）

用户看过上一轮的产出后又提两条，都已修：

1. **抬头去套话**：修订理由批注不再写「— 已在此处标为修订，请确认后接受或拒绝」，
   冲突批注不再写「— <规则通用描述>」。抬头只留类别标签，
   判据是"这句话有没有增加信息"。写长了评审人就不看了。
2. **锚定精确到字符**：ADR-031 里"边界对齐到 run、多圈一点无妨"的判断在真实文档上
   是错的——run 合并后一整段常常只剩一只 run，"多一点"等于"整段"。
   改为先把锚点切成独立 run（`ooxml.isolate_span`）。
   这不违反 D9：文本逐字不变、rPr 深拷贝，与修订回写同一套机制、同一套负向对照。

### 2026-08-10 第二轮真实运行后的修正（ADR-031）

用户实跑后报了两个现场问题，都出在回写的最后一厘米——判定全对，交付物读不出来：

1. **修订处没有批注，看不出为什么改**。原实现认为"已落笔为修订就不必再批注"，
   但修订标记只显示改成了什么。现在每处修订同时写一条 `kind: revision` 的批注，
   正文只答"为什么改"，并按 `del_id`/`ins_id` 精确锚在这处改动上
   （拒绝视图圈住的正是原文，接受视图正是建议）。
   顺带修掉一个静默丢失：计划了修订但定位失败的条目原先既无修订也无批注。
2. **批注只选中前面几行**。根因是把"定位用的 run 集合"当成了"锚定用的 run 集合"：
   含 `w:br`/`w:tab`/图形的 run 与既有修订被排除在范围外，段落末尾有软换行时
   范围就止于换行之前，整段在一个含 `w:br` 的 run 里时范围直接塌成零长度。
   范围边界改取 `w:p` 的直接子节点，定位不到即退回整段；
   冲突批注锚点的 `[:40]` 硬截断同时去掉。
3. **校验补齐**：第四项原来只查 Start/End 配对，上述三种现场全都能过。
   现在加查"范围内有正文"与"范围覆盖完整锚点"，并配两条负向对照。

**第四轮：错词表的子串误命中审计（`pass1-typo` 的前置）**

**第六轮：术语表的压制方向（`pass0-glossary`）**

术语表有个别处没有的性质：**它是唯一一个用来压制发现的输入**（N7、L05）。
N7 的 fallback 判据原本是「跨度里出现该术语就压制」——用户表里放一个
「系统」或「平台」，含这两个字的发现就全被静默吞掉。实测三条全丢。
这个场景不是构造的：SKILL.md 本就建议把 Pass 0 抽出的术语表作为下一轮输入，
而 `min_term_freq: 3` 的预筛只会让通用高频词更容易入选。已改为
「建议里该术语没了才压制」，详见 ADR-030。

**这六份基线的效力边界要说清楚**：跑它的模型能力高于本技能面向的"中等能力模型"，
所以 0% 误报是**上限而非典型值**。它证明的是「prompt 与不改清单本身不诱导误报」，
不能替代中等模型上的实测。A/B 盲测的位置一致率（M2 验收项）也还没测。

### 1. 全部 LLM 侧 prompt 未经真实模型验证 ⚠️ 最重要

`pass1-review.md` 已由上面那轮基线覆盖，**其余六份仍未用真实模型跑过**：
`pass0-glossary` / `pass1-extract` / `pass2-verify` / `pass4-adjudicate` /

- Pass 4 裁定的准确性
- 事实抽取的完整性 —— 它直接决定 L 规则的检出率，是逻辑通道的真正瓶颈
- 错别字裁定在白名单陷阱上的准确率（脚本侧零候选已验，裁定侧未验）
- 范式要件裁定的一致性

`pass1-review` / `pass1-extract` / `pass2-verify` 三份已覆盖（后者是补齐了脚本侧）。
**六份 prompt 的脚本侧都已审过一遍。剩下的是纯模型侧指标**：
`pass1-typo` / `pass1-pattern` / `pass4-adjudicate` / `pass0-glossary`
四份的裁定准确率，以及 M2 的位置一致率在中等模型上的实测值。 三者的脚本侧现在都已 fail-closed，
漏答不会变成误报，只会变成漏报——这让"未实测"的风险从"可能写错东西"
降到了"可能少写东西"。

**M2 的位置一致率现在可测但未在中等模型上测过**，这是它真正的用武之地。

### 2. M7 压测未做

`docs/SPEC.md` §7.4.3 的性能表是**建模估算，非实测**。需要 ≥500 页真实文档：
跑通全流程、记录实测页密度、确定 `parallelism` 最优值，然后回填该表。

### 3. M8 错别字通道未标定召回率

通道已接通、词表已扩到 210 条、白名单陷阱在回归里零误报，但：
- **未在"含 100 个已知错别字"的真实语料上测过召回率**（SPEC §15.1 M8 要求 ≥85%）。
  当前 fixture 只植入 8 处，够验证链路，不够标定。
- 召回率上限 = `common-typos.txt` 的覆盖范围。扩表是唯一杠杆，
  **不得放宽闸门②的 A1 阈值**（ADR-023）。
- 未登录词检测按 ADR-023 不做。若将来要做，需先决定是否内置 5–10 万词表
  （数 MB + 词表来源与分发许可），这是个待用户拍板的取舍。

### 3b. M9 范式规则包等用户补真实正反例

`assets/patterns/builtin-examples.yaml` 里的两条（风险条目、接口描述）是**示例**，
用来给出规则的写法与粒度。真实范式是场景特定的，需要用户提供正例/反例后才能填。
在拿到真实规则包并人工核对误报率之前，`severity_cap` 不要放宽（SPEC §15.1 M9）。

### 4. 未在 Windows / macOS 上验证

`convert_doc.py` 的 Word COM 分支、`workspace.py` 的文件系统类型探测（见 ADR-014）
都只在 Linux 上跑过。

### 5. 多会话协作只做了单元级验证

令牌栅栏（退出码 9）、回写阶段禁止接管已在回归中覆盖；但"两个会话真正并发处理同一文档、
无重复处理无丢片"这项 M6 验收**未做端到端验证**。

## 未决问题

- **L29–L32 的误报率没有基线。** SPEC 要求"首轮跑完应人工核对其误报率，再决定是否提升
  其地位"。目前默认 `coverage_rules_to_comment: false`（只进报告），在拿到基线前不要改。
- **XSD 校验是已知缺口**（ADR-007）。若要补齐，需决定是否内置 ECMA-376 schema
  （数 MB + 分发许可问题）。
- **`report.py` 的「术语表覆盖率」一节按 `preferred` 是否出现在全文判定**，
  对有 scope 限定的术语会偏乐观。真实语料上看过再决定要不要按 scope 细化。
- **P 类的误报率没有基线。** 与 L29–L32 同样的处境：`severity_cap: Medium`
  是保守缺省，拿到真实规则包的基线前不要放宽，也不要给 P 类开修订口子。
- **同一实体关系在多个段落各出现一次时，L04 会产出多条候选。** 实测基线里
  「边沿节点/边缘结点」出了 2 条。不是误报，但评审人会看到重复条目。
  跨片、跨段的候选去重是 Pass 3 的已知薄弱点，等真实语料上看过再决定合并策略。
- **范式规则只看单个段落。** "风险表述分散在连续三段里"会被判成缺要件。
  规则该用 `min_chars` 或更严的 `paragraph_regex` 把这类段落排除；
  是否要支持跨段落范式，等真实语料上遇到了再定。
