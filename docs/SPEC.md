# docx-content-review 技能开发规格说明书（SPEC v1.1）

> 本文档是交付给编码 Agent 的实现规格（**v1.1**）。实现方应严格遵循本文的目录结构、CLI 契约、数据 schema 与判定规则；对本文未规定的细节可自行决策，但需记入 `docs/decisions.md`。

---

## 0. 项目元信息

| 项 | 值 |
|---|---|
| 技能名 | `docx-content-review` |
| 运行平台 | XAgent 智能体 |
| 定位 | 对 Word 文档（0–3000 页）执行语义、语病、全文逻辑性审查，输出审查报告并可选回写修订/批注 |
| 上下文窗口 | 主 Agent 与子 Agent 均为 128k，单次占用目标 ≤ 60%（≈76k tokens） |
| 模型假设 | 中等能力通用模型，**不假定具备顶尖推理能力** |
| 依赖策略 | 自闭环，所有 docx 处理能力内置于本技能目录，不依赖外部技能 |
| 网络 | 运行期不依赖网络 |

**文案约束**：技能内所有文件（SKILL.md、references、scripts 注释、报告模板、日志文案）一律使用"Agent / 主 Agent / 子 Agent"表述，不出现特定厂商模型名称。frontmatter 中以 `platform: XAgent` 标识运行平台。

## 1. 交付目标与非目标

### 1.1 目标

1. 输入 `.doc` / `.docx`，输出结构化审查结果。
2. 覆盖三类审查：**语病（表层语言错误）**、**语义（表达清晰度/歧义）**、**逻辑性（跨章节一致性）**。
3. 交付物 = **审查报告 + 带修订的 Word 文档**，修订可由人工逐条接受/拒绝。
4. 支持 3000 页规模，支持中断后续跑。
5. 默认严格度取向为"平衡"，但**落笔（生成修订）门槛强制收紧**。

### 1.2 明确的非目标

- 不做格式/排版规范审查（由 `docx-format-audit` 技能负责，两者不得功能重叠）。
- **不修改任何样式**：字体、字号、行距、缩进、编号、颜色、段落格式、页面设置一律不动（见 D9）。即便审查过程中发现格式问题，也不报告、不修改。
- 不做事实性核查（不判断文档陈述与外部世界是否相符），只做**文档内部自洽性**检查。
- 不做文风改写、不做润色、不做压缩改写。
- 不处理 PDF、不处理 WPS 专有格式。
- 不保证发现所有问题；召回率不是主要优化目标。

## 2. 核心设计决策（实现方不得擅自更改）

### D1：逻辑性审查降维为「抽取 → 脚本比对 → 局部复核」

分片后的子 Agent 是失忆的，无法感知其他分片内容。因此**禁止**让子 Agent 直接判断跨章节冲突。取而代之：

```
Pass 1（LLM，逐片）  抽取结构化事实 → ledger（台账）
Pass 3（脚本，零 LLM）在台账上做确定性比对 → 冲突候选
Pass 4（LLM，仅候选）把冲突双方原文同时给出 → 裁定真伪
```

**理由**：跨片比对是集合运算，不是语言理解任务；交给脚本可获得 100% 召回且零幻觉，同时大幅降低 token 成本，并规避中等能力模型的能力短板。

### D2：不使用模型自评置信度作为阈值

**禁止**在任何 prompt 中要求模型输出 `confidence: 0.0~1.0` 并据此卡阈值。

**理由**（实证依据见 §14）：模型言语化置信度存在系统性过度自信与分数饱和——分值集中于 0.9/1.0 少数分箱，不存在能有效区分真假的阈值点；且已作出判断的 Agent 倾向为自身判断辩护而非批判。此类分数至多可作排序信号，不能作为概率使用。

**替代方案**：四道可工程化闸门（§8）。

**允许的例外**：可以输出 `priority_score`，但它必须**完全由脚本计算**（来源：规则强度 + 类别权重 + 证据数量 + 二次复核一致性 + 冲突涉及的章节跨度），且**不得参与任何自动判定**，仅用于 `issues.xlsx` 的展示排序。几千条问题需要排序，但排序依据不能来自模型自评——否则它会以另一个名字变回阈值。

### D9：样式绝对不变

**本技能不修改任何字体、字号、行距、缩进、编号、颜色、段落格式或页面设置。** 它只改动文本内容，且只以修订/批注形式改动。

这条约束最容易被**无意违反且静默失败**，因此必须写成可校验的规则（实现见 §6.3、校验见 §6.5）：

1. 替换 run 内部文字需将该 run 拆为三段（前/目标/后），**每一段都必须深拷贝原 `rPr`**。漏拷即套用默认样式——三号字变五号、仿宋变等线，且只在用户接受修订后才显现。
2. **禁止产生任何格式修订标记**：`w:rPrChange`、`w:pPrChange`、`w:sectPrChange`、`w:tblPrChange`、`w:tcPrChange`、`w:trPrChange`。
3. `styles.xml`、`theme/theme1.xml`、`fontTable.xml`、`numbering.xml`、`settings.xml`、`webSettings.xml` 的字节哈希必须与原文档完全一致。
4. `document.xml` 中不属于本次修订范围的 `rPr` / `pPr` / `sectPr` 节点，内容与数量必须不变。

格式规范类问题（字号不统一、行距不一致等）属于 `docx-format-audit` 技能的职责，本技能**发现也不报告、不修改**，避免两个技能对同一文档产生冲突改动。

### D8：论证链审查降维为覆盖性检查

"论断缺乏证据""结论强度超过证据"这类判断是开放式的、无客观阈值的，与 §12 的中等模型约束和精确率优先取向直接冲突，**不进入 v1 主流程**。

但其中**可脚本化的部分必须做**——凡是"A 类元素应当有对应的 B 类元素"的检查，本质是集合差集运算，不是强度判断：

| 可脚本化（v1 做，L29–L32） | 不可脚本化（v2 开关，默认关闭） |
|---|---|
| 目标提出但无对应举措 | 证据是否充分 |
| 举措提出但无验收指标 | 结论强度是否超过证据 |
| 量化承诺无度量方式 | 是否存在绝对化表达 |
| 章节标题承诺的内容正文缺失 | 论证是否严密 |

覆盖性规则**依赖抽取完整性**，漏抽即误报，因此严重度上限 Medium，措辞统一为"未检索到对应的 X，请确认"，**默认只进报告，不进批注**。

不可脚本化部分由 `argument_review` 开关控制，默认 `off`，见 §9.6。

### D3：修订与批注分流，硬规则

| 条件 | 动作 |
|---|---|
| 存在**唯一确定**的正确替换文本 | 生成 `w:ins`/`w:del` 修订 |
| 不存在唯一正确答案（歧义、逻辑冲突、指代不明） | 生成 `w:comment` 批注，**不动正文** |
| 仅风格倾向 | 只进报告，不入文档 |

**任何一条修订，其 `suggested_text` 必须非空、必须通过编辑距离检查、必须通过二次复核。** 三者缺一即降级为批注。

### D4：双门槛

- `report_threshold`：控制哪些问题进报告。默认 `balanced`。
- `apply_threshold`：控制哪些问题落笔为修订。**强制 `conservative`，不可通过配置放宽到 balanced 以上**。

### D5：无外部术语表 → 新增 Pass 0

流水线为 5 段（Pass 0–4），Pass 0 全文扫描自建术语/命名台账，必须在 Pass 1 之前整体完成。

### D6：源文档绝对不可变

**源文档在整个技能生命周期内视为只读，任何步骤不得对其执行写操作。**

- Pass -1 的**第一个动作**是复制源文档到工作目录，此后所有路径引用一律指向副本。
- 格式转换（doc→docx）的输出目录必须显式指定为工作目录，**不得使用工具默认行为**——LibreOffice 的 `--outdir` 若省略会在源文件同级目录产出，Word COM 的 `SaveAs` 若不指定完整路径同理。
- 所有写文件的脚本必须调用统一守卫函数 `guard_write_path(path)`：若目标路径不在本次运行的工作目录之下，**抛异常并终止**，不做任何降级。
- 运行开始与结束时各计算一次源文档 `sha256`，不一致即判定运行失败并在报告中告警（防御性检查，用于捕获守卫失效）。
- 复制失败（源文件被占用、磁盘空间不足、目标目录无写权限）→ 立即终止并给出原因，**不得尝试原地操作**。

### D7：产物写入 Agent 工作目录，按文档隔离

**技能目录在运行期视为只读**，不得产生任何运行产物。所有中间产物与交付物写入 Agent 工作目录下的独立子树，且**按源文档内容哈希隔离**，以支持同一工作目录下对多个文档并行/交替执行。详见 §11。

## 3. 总体流水线

```
[Pass -1] 工作目录初始化 → 源文档复制（源文档此后只读）
          → 环境探测 → doc→docx 归一
          探测失败 / 复制失败 → 终止并给出指引
             ↓
[Pass 0]  文档解析 & 全局台账初建
          解包 → merge runs → 段落级 ID → 标题树
          → 导入外部术语表（可选，高优先级/兜底两层）并自检
          → 轻量扫描抽取：候选术语、缩略语、专名、编号体系
          → 三层合并 → glossary.merged.json（唯一出口）
             ↓
[Pass 1]  分片（按标题树，硬上限兜底）→ 子 Agent 并/串行处理
          每片输出两份产物：
            a) issues-<chunk>.jsonl   局部语病/语义问题
            b) facts-<chunk>.json     结构化事实台账条目
                                      （原样记录写法，禁止术语归一化）
             ↓
[Pass 2]  局部问题过闸（脚本 + 可选二次复核）
          原文 exact match 校验 → 编辑距离校验 → 不改清单过滤
          → 二次独立复核 → issues-verified.jsonl
             ↓
[Pass 3]  全局台账冲突检测（纯脚本）
          按 §9 规则表跑 → conflicts-candidate.json
             ↓
[Pass 4]  冲突裁定（LLM，仅候选，双方原文同时入上下文）
          → conflicts-verified.json
             ↓
[输出]    report.md + issues.xlsx + reviewed.docx（修订+批注）
```

**主 Agent 上下文里只保留 manifest 摘要与统计数字，永不保留问题正文。** 子 Agent 返回值必须是 `{文件路径, 计数, 状态}`，不得返回问题内容。

## 5. Pass -1：工作目录初始化、源文档保护与格式转换

### 5.1 执行顺序（不可调换）

| # | 动作 | 失败处理 |
|---|---|---|
| 1 | 解析工作目录（§11.1），创建隔离目录，取运行锁 | 无写权限 / 锁被占用 → 终止 |
| 2 | 计算源文档 `sha256`、记录大小与 mtime | 文件不存在或不可读 → 终止 |
| 3 | 磁盘空间预检：可用空间 ≥ 源文档大小 × 6 | 不足 → 终止并报出所需空间 |
| 4 | **复制源文档**到 `work/source-copy.<ext>` | 复制失败 → 终止，不得原地操作 |
| 5 | 校验副本 `sha256` 与源一致 | 不一致 → 终止 |
| 6 | 环境探测（5.2） | 无可用转换器且输入为 `.doc` → 终止 |
| 7 | 若为 `.doc`：转换副本 → `work/normalized.docx`，输出目录显式指定 | 转换失败或产物不可解包 → 终止 |
| 8 | 写入 `manifest.json` 初始状态 | — |

**第 4 步之后，源文档路径只允许出现在两处**：manifest 的 `source` 字段（记录用途）和结束时的 sha256 复核。其余任何脚本参数、日志、临时文件路径中都不得再出现源路径。实现时应在 `workspace.py` 提供 `resolve(kind)` 统一取路径，杜绝各处硬编码。

**倍数 6 的来源**：副本 1× + 转换产物 1× + 解包目录约 1.5× + 分片文本约 1× + 回写产物 1× + 余量 0.5×。

### 5.2 环境探测

`scripts/env_probe.py` 输出 JSON 到 stdout：

```json
{
  "os": "windows|linux|darwin",
  "converters": [
    {"name": "word_com",   "available": true,  "detail": "Word.Application 16.0"},
    {"name": "soffice",    "available": false, "detail": "not found in PATH"},
    {"name": "unoconv",    "available": false, "detail": null}
  ],
  "python": "3.11.6",
  "can_convert_doc": true
}
```

探测顺序：

- **Windows**：先试 Word COM（`win32com.client.Dispatch("Word.Application")`，用后必须 `Quit()` 且捕获异常确保进程不残留）；再试 `soffice`。COM 转换必须以 `Documents.Open(copy_path, ReadOnly=True)` 打开**副本**，并用 `SaveAs2` 指定工作目录内的完整目标路径。
- **Linux / macOS**：依次探测 `soffice`（`--headless --convert-to docx --outdir <工作目录>`，`--outdir` **必须显式传入**）、`libreoffice`、`unoconv`。同一机器上多个转换任务并发时需为每次调用指定独立的 `-env:UserInstallation=file:///<工作目录>/.uno`，否则 LibreOffice 会因用户配置目录冲突而失败。

**失败即终止**。终止时必须输出可执行的修复指引，不得静默降级、不得尝试用文本提取绕过：

```
[终止] 检测到输入为 .doc 格式，但当前环境无可用的格式转换工具。
当前系统：Linux (Ubuntu 22.04)
已探测：soffice(未找到) libreoffice(未找到) unoconv(未找到)
请安装其一后重试：
  Debian/Ubuntu:  sudo apt-get install -y libreoffice-writer
  RHEL/CentOS:    sudo yum install -y libreoffice-writer
或在 Windows 环境下运行本任务（需已安装 Microsoft Word）。
```

`.docx` 输入跳过本步。转换后必须校验产物可解包且 `word/document.xml` 存在，否则同样终止。

## 6. 内嵌的 docx 处理能力（自闭环）

不整体 vendor 外部技能，只内嵌本技能实际需要的四项能力，全部写入 `references/ooxml.md` + `scripts/`：

### 6.1 解包与 run 合并（必须）

`.docx` 是 ZIP。解包后**必须先删除所有符号链接条目**（外部来源文档不可信），再执行 run 合并。

**关键约束**：Word 会因修订 ID、拼写检查标记等把一个句子拆成多个 `<w:r>`，因此**文档中肉眼可见的短语，在 XML 中往往不是连续字符串**。定位与回写前必须合并相邻的同格式 run（合并只改结构不改内容与渲染）。这是所有定位失败的首要原因。

编辑 `word/document.xml` 时**禁止重新格式化或美化 XML**。重新打包用 `zip -Xr`。

### 6.2 段落级 ID 与定位（必须）

`extract.py` 为每个段落分配稳定 ID，输出 `paragraphs.jsonl`：

```json
{"pid":"p-000412","xpath_hint":"/w:document/w:body/w:p[412]","heading_path":["3 系统设计","3.2 数据层","3.2.1 存储选型"],"level":3,"style":"Normal","text":"……","char_len":186,"in_table":false,"is_code":false,"page_hint":137}
```

- `heading_path` 是逻辑审查的核心上下文，必须准确。
- `is_code` / `in_table` 用于命中不改清单（代码块、命令行、配置示例不做语言审查）。
- `page_hint` 为估算值，仅用于报告定位，不参与判定。

### 6.3 修订回写（必须）

用 `<w:ins>` / `<w:del>` 包裹 run，属性含 `w:id`、`w:author`、`w:date`。

**要点**：
- 删除态的文本元素是 `<w:delText>`，不是 `<w:t>`。
- 段落标记删除（`<w:pPr><w:rPr><w:del .../></w:rPr></w:pPr>`）语义是"把本段并入下一段"；删除整段 = 段落标记删除 + 每个 run 外包 `<w:del>`。
- `<w:del/>` 必须排在 `rPr` 其他子元素之前，元素顺序受 schema 强制。
- 本技能**只做行内文本替换，不做段落删除、不做段落合并、不做段落新增**。这是刻意的能力约束，用于把回写风险降到最低。
- **run 拆分与 `rPr` 深拷贝**：替换 run 内部的一段文字，需将原 run 拆为「前段 / 被删段 / 后段」三个 run。三者的 `rPr` 必须是原 `rPr` 的**完整深拷贝**（含 `rFonts` 的 `w:ascii`/`w:eastAsia`/`w:hAnsi`/`w:cs` 四个属性、`sz`/`szCs`、`b`/`i`/`color`/`u`/`spacing` 等全部子元素）。新插入的 run 同样继承该 `rPr`。**漏拷或部分拷贝会导致 Word 套用默认样式，且只在接受修订后显现。**
- **禁止输出任何格式修订标记**：`w:rPrChange`、`w:pPrChange`、`w:sectPrChange`、`w:tblPrChange`、`w:tcPrChange`、`w:trPrChange`。这些元素的存在即表示本技能改动了格式，违反 D9。

回写后必须运行 `validate_docx.py`，四项检查任一失败即判定本次回写失败，**回滚到原文档**并报错：

1. **XSD 校验**通过。
2. **无未追踪变更**：与原始文档比对，任何未被 `w:ins`/`w:del` 包裹的文本变更都要报告——这类改动在"接受修订后"视图里不可见，极易无意产生。
3. **样式不变性**（D9）：
   - `styles.xml`、`theme/theme1.xml`、`fontTable.xml`、`numbering.xml`、`settings.xml`、`webSettings.xml` 的字节哈希与原文档完全一致；
   - `document.xml` 中不存在 `w:rPrChange` / `w:pPrChange` / `w:sectPrChange` / `w:tblPrChange` / `w:tcPrChange` / `w:trPrChange`；
   - 逐 run 比对：本次未改动的 run，其 `rPr` 序列化结果不变；本次新增的 run，其 `rPr` 与来源 run 逐属性相等。
4. **批注锚定完整**：每个 `commentReference` 都有配对的 `commentRangeStart`/`End`，且 id 在 `comments.xml` 中存在。

### 6.4 批注回写（必须）

**必须区分核心层与增强层，不可混为一谈**：

| 层 | 文件 | 缺失后果 |
|---|---|---|
| **核心层** | `comments.xml` + `document.xml` 中的 `<w:commentRangeStart>` / `<w:commentRangeEnd>` / `<w:commentReference>` + 关系文件 + 内容类型覆盖项 | 批注不可见——**这层必须成功** |
| **增强层** | `commentsExtended.xml`、`commentsIds.xml`、`commentsExtensible.xml` | 仅失去回复线程、已解决标记等特性，**批注照常可见** |

核心层结构自 Office 2007 起稳定；增强层随版本演进，写入失败或目标 Word 版本不支持时**降级为仅核心层并在报告中记录，不得导致整体失败**。

仅写入这些文件而不在 `document.xml` 中锚定，批注不可见——锚定属于核心层，不可省略。

`apply_comments.py` 必须一次性处理全部批注（3000 页可能上千条），避免反复解包/打包。

**批注是逻辑审查的主要交付出口**：L01–L24 中绝大多数动作是批注（模型无法判断冲突双方孰对孰错，只能提示人工确认）。因此批注能力不可延后到后续版本——延后等同于砍掉逻辑审查的交付路径。相较之下，修订才是高风险动作：它直接改动正文，误报即污染交付物；批注纯附加、可整体回滚。二者的风险排序不可颠倒。

## 7. 分片策略与上下文预算

### 7.1 预算表（单个子 Agent，128k 窗口）

| 组成 | 预算 |
|---|---|
| 技能指令 + 类型体系 + 不改清单 | ≤ 9k tokens |
| 全局台账摘要（术语表 + 命名规范摘要，裁剪版） | ≤ 4k tokens |
| 分片正文 | **≤ 15k tokens（默认，可配置 8k–22k）** |
| 上文衔接（前一片末尾 2 段） | ≤ 1k tokens |
| 输出预留 | ≤ 12k tokens |
| **合计** | **≈ 41k / 128k ≈ 32%** |

按中文近似 1 汉字 ≈ 1 token 估算，15k tokens ≈ 1.5 万字 ≈ **18–20 页**。

### 7.2 必须按实际 token 计量，不得按字数估算

"1 汉字 ≈ 1 token"只对纯中文散文成立。规划类、可研类文档中的表格、参数、英文专名、编号、单位符号在中文 tokenizer 下 token 密度显著更高，按字数估算会**系统性低估**，导致实际输入远超预算。

因此 `chunk.py` 必须：

- **实际调用 tokenizer 计数**，而非按字符数换算；
- 输出双计量，供校验与排障：

```json
{"chunk_id":"0042","text_tokens":15120,"context_tokens":28640,"pages_est":19}
```

- `context_tokens` = 正文 + 指令 + 术语表摘要 + 上文衔接 + 输出预留，**以它作为切分判据**，超过 `max_context_tokens`（默认 45000）即重新切分；
- tokenizer 不可得时，使用保守系数 **×1.6** 兜底，并在 manifest 中标记 `token_estimated: true`。

#### 7.2.1 页密度校准

**页数只用于报告定位，绝不作为切分判据。** 但定位精度对 2000 页文档很重要——页码差 5 页和差 50 页，人工核对体验完全不同。

页密度因排版差异极大：紧排版的纯正文可达 700+ 字符/页；三号字（16pt）+ 28 磅行距的公文/规划类版式，实测平均约 **300 字符/页**（纯文字页可到 600，其余被标题、表格、图、留白占据）。用固定常数换算必然失准。

**校准方法**：`docProps/app.xml` 通常存有 Word 写入的 `<Pages>` / `<Characters>` / `<Words>`，据此可算出该文档自身的真实密度。

优先级：
1. `app.xml` 存在且数值合理 → 用文档自身密度；
2. 文档含显式分页符 → 按分页符插值；
3. 均不可用 → 退回常数 400 字符/页，并在 `paragraphs.jsonl` 与报告中标记 `page_estimated: true`。

> `app.xml` 的值由 Word 在上次保存时写入。非 Word 生成或经工具处理的文档可能缺失或过期，因此第 1 项必须做合理性校验（`Characters / Pages` 落在 100–1200 区间）。

**表格的 token 密度显著高于正文**（分隔符、表头重复、单元格边界标记），因此表格密集的文档若按页数切分，会在表格区系统性溢出。这是必须按实际 token 计量的直接原因。

### 7.3 单片模式（不分片）判定

**仅当全文正文 ≤ 22k tokens 时**走单片模式。**判据是 token，不是页数**——同样 22k tokens，紧排版对应约 30 页，稀排版（三号字 + 28 磅行距，约 300 字符/页）可达约 60 页。

> 注：页数与 token 不是固定比例，相差可达一倍以上。任何以页数为阈值的实现都会在某类排版下失效。`chunk.py` 必须先计数再判定，报告中的页数换算仅供人阅读。

### 7.4 并发执行模型与性能预期

**与 §11.3 的区别**：§11.3 处理的是**用户意外开启多会话**（被动、需协调）；本节处理的是**主 Agent 主动调度多个 subAgent**（主动、可编排）。两者共用同一套分片 claim 机制，无需额外设计。

#### 7.4.1 工作池模式（不做静态分配）

主 Agent 启动 `parallelism` 个 subAgent，每个执行同一循环：

```
loop:
  尝试 claim 下一个 pending 分片（O_EXCL）
  claim 失败 → 取下一个；全部失败 → 退出
  处理 → 原子落盘 → 删除 claim
```

**主 Agent 不做任何分配决策**，只需知道"还剩几片"。这正是 claim 机制的价值：调度逻辑为零，且单个 subAgent 崩溃时其 claim 过期即被回收，其余不受影响。

主 Agent 上下文开销：每个 subAgent 返回 `{path, count, status}`，10 个并发也只有几百 token。

#### 7.4.2 三个必须处理的坑

1. **退避会超出 claim TTL。** 模型服务限流触发指数退避后，单片处理时间可能超过 `chunk_claim_minutes: 20`，导致 claim 被回收、另一个 subAgent 重复处理同一片。**subAgent 必须在每次 LLM 调用前后续期自己的 claim**，与 §11.3.7 的租约保活同理。
2. **并发度不宜过高。** Pass 1 单次输入约 28k tokens，10 并发即 280k tokens/批，容易触发服务端限流，反而更慢。默认 `parallelism: 5`，上限建议 8。实际值应由压测确定。
3. **Pass 2 不与 Pass 1 流水线并行（v1）。** 理论上某片完成即可复核，但两类任务会竞争同一模型配额，且编排复杂度显著上升；而 Pass 2 在并发后仅占总耗时约 5%。**v1 采用 Pass 1 全部完成后再启动 Pass 2 的简单串行**，流水线并行留待 v2 视实测决定。

#### 7.4.3 性能预期（2000 页基线）

> 以下为**建模估算，非实测**。实现方应在 M7 压测中用真实数据替换本表，并写回 `docs/progress.md`。
> 假设：**300 字符/页**（三号字 + 28 磅行距的实测密度）→ 2000 页 ≈ 60 万字符；token 密度系数 1.2；`max_text_tokens: 15000` → 约 **48 片**。

| 阶段 | 调用次数 | 单次耗时假设 | 串行耗时 |
|---|---|---|---|
| Pass 0 术语抽取（经 9.1.4 预筛后） | ~10 | 60s | 10 min |
| Pass 1 审查（扣除纯表格片） | ~42 | 80s | 56 min |
| Pass 1 事实抽取 | ~48 | 100s | 80 min |
| Pass 2 复核（批量 10） | ~72 | 15s | 18 min |
| Pass 4 裁定 | ~20 | 30s | 10 min |
| 脚本部分（解包/分片/Pass 3/回写） | — | — | ~20 min |
| **合计** | **~192 次** | | **≈ 3.2 小时** |

| `parallelism` | 预计总耗时 |
|---|---|
| 1 | ~3.2 h |
| 3 | ~1.2 h |
| **5（默认）** | **~1.0 h** |
| 8 | ~0.8 h |

Token 量级：输入约 **300 万**，输出约 25 万。

> **页密度对估算的影响极大。** 若文档为紧排版（700+ 字符/页），上表的片数与耗时需按比例上调约 2 倍。因此 M7 压测必须记录实测密度，并据此重新标定本表；不同排版的文档不可共用同一份预期。

**脚本部分不随并发缩短**（Pass 3、回写、校验为独占单写），因此并发度超过 8 后收益迅速衰减——瓶颈转移到脚本段与限流。

### 7.5 分片规则

1. **优先按标题树切**：以 H2 为主切点，H3 为次切点。
2. **硬上限兜底**：任一片超过 `max_tokens` 时按段落边界强制切开，不切断段落，不切断表格。
3. **不跨切点**：表格、代码块、列表整体不可被拆分；单个超长表格独立成片。
4. **携带上下文头**：每片开头注入 `heading_path` 全路径 + 前一片末尾 2 段（仅作理解，**明确标注为"参考上文，不在本次审查范围"**）。
5. **重叠区去重**：重叠段落产生的问题按 `pid` 去重，保留首次出现。
6. **纯表格片跳过审查调用**：`tables_language_check: true` 时表格不做语病审查，因此纯表格分片（正文段落占比 <10%）**只发起事实抽取调用，不发起审查调用**。规划类、可研类文档表格密度高，此项可省约 10–15% 的调用量。分片时标记 `chunk_type: "table_only" | "mixed" | "text"`。

## 8. 误报抑制：四道闸门

这是本技能的质量核心。四道闸门串联，任一不通过即淘汰或降级。

### 闸门① 类型白名单（prompt 层）

问题必须归入 `references/taxonomy.md` 中枚举的类别之一（**总数不超过 12 类**），且必须引用该类的 `rule_id`。无法归类的一律丢弃。

**A 类 · 客观错误**（有唯一正确答案 → 可生成修订）
- `A1` 错别字/形近字误用 —— **v1 由 LLM 顺带发现，召回率低（见 §9.7），M8 后由独立通道接管**
- `A2` "的/地/得"误用
- `A3` 标点误用（含中英标点混用、括号书名号不配对）
- `A4` 成分残缺（缺主语/谓语/宾语中心语）
- `A5` 搭配不当（动宾、主谓、定中）
- `A6` 关联词误用或不搭配（"虽然…但是"错配、"不但…反而"）
- `A7` 完全重复赘余（"大约…左右"、"目前正在…中"叠用、连续重复词）
- `A8` 数字/单位书写错误（同一文档内单位符号不统一、千分位错位）

**B 类 · 需语境判断**（默认只生成批注）
- `B1` 指代不明（"其/该/它"指向多义）
- `B2` 句法歧义（多重定语造成两解）
- `B3` 长句结构混乱（≥80 字且主干不可辨）
- `B4` 主客体颠倒
- `B5` 逻辑连词与实际语义关系不符（前后无因果却用"因此"）

**C 类 · 主观倾向**（默认关闭；`thorough` 下仅进报告，永不入文档）
- `C1` 表达冗长
- `C2` 段落过长（≥600 字未分段）

### 闸门② 可验证性（脚本层，`verify_span.py`）

1. **原文逐字校验**：`original_text` 必须在该分片正文中 exact match（仅允许空白字符归一化）。不匹配 = 幻觉 = **直接丢弃，不做修补**。
2. **修改幅度校验**（仅对有 `suggested_text` 的条目）：**按错误类型分别校验，不使用统一的编辑距离阈值**。多数类别存在比编辑距离更强的结构约束：

   | 类别 | 校验规则 |
   |---|---|
   | `A1` 错别字 | `suggested` 与 `original` 长度差 ≤2，且差异字符数 ≤3 |
   | `A2` 的地得 | 差异字符必须只在 {的, 地, 得} 集合内 |
   | `A3` 标点 | **剥离标点后的字符序列必须完全一致** |
   | `A4` 成分残缺 | 只增不删：`original` 必须是 `suggested` 的子序列 |
   | `A5` 搭配不当 | 编辑距离 ≤ min(12, len×0.3) |
   | `A6` 关联词 | 差异仅限关联词表内的词 |
   | `A7` 赘余 | **只删不增：`suggested` 必须是 `original` 的子序列** |
   | `A8` 数字单位 | 差异仅限数字、单位符号、分隔符 |
   | `L25/L26` 术语 | 差异必须完全落在术语表登记的 `forbidden`/`variants` → `preferred` 映射上 |

   全部不通过 → **降级为批注**，清空 `suggested_text`。
   兜底：任何类别的编辑距离超过 `min(30, len×0.4)` 一律降级，不论上表是否通过。
3. **长度校验**：`original_text` 长度须在 4–120 字之间。过短无法定位，过长说明模型在圈整段。
4. **单片上限**：每片最多上报 `max_issues_per_chunk`（默认 20）。超出按 severity 排序截断，并在该片记录 `truncated: true`。此项用于抑制模型"凑数"倾向。

   **但必须为 B 类保留下限席位**（`min_b_class_slots`，默认 5）。纯按 severity 截断在这里会退化成按类别截断：A 类恒 `High`、B 类恒 `Medium`，于是一片里只要 A 类满 20 条，B 类就一条都出不来——指代不明、歧义、主客体颠倒会被错别字与标点整组挤掉。这与 §9.7 论证错别字必须独立配额的机制相同（配额挤占 + 重要性排挤），只是受害者换成了 B 类；B 类与 A 类同出一次调用，拆不成独立通道，因此改为保底席位。

### 闸门③ 不改清单（脚本 + prompt 双层，`references/never-flag.md`）

以下情形**明确禁止上报**，并在 prompt 中以**反例 few-shot** 形式给出（每条至少 2 个具体反例）：

| # | 禁止上报的情形 |
|---|---|
| N1 | 同义/近义词替换（"使用"↔"采用"↔"运用"） |
| N2 | 语序偏好调整（状语前置/后置） |
| N3 | 主动被动语态转换 |
| N4 | 书面语/口语色彩调整 |
| N5 | 句子长短偏好（未触及 B3 判定要件的） |
| N6 | 虚词增删（"的/了/着"等，A2 情形除外） |
| N7 | 术语的合法别名（依据 `glossary.json` 的别名组判定） |
| N8 | 行业惯用简称、产品代号、内部代号 |
| N9 | 代码块、命令行、配置示例、日志片段、文件路径内的一切内容 |
| N10 | 引用的法规/标准/合同原文（由引号或引用样式标识） |
| N11 | 表格单元格内的省略式表述 |
| N12 | 图表标题、编号、页眉页脚的固定格式 |
| N13 | 数字用法（阿拉伯数字 vs 汉字数字）——无规范输入时不判 |
| N14 | 标题的名词短语式表述（无谓语不算成分残缺） |

`filter_neverflag.py` 对 N7–N12 做脚本级硬过滤（依据 `is_code`、`in_table`、`glossary` 别名组、引用样式标记），不依赖模型自觉。

### 闸门④ 二次独立复核：盲测 A/B（LLM，`pass2-verify.md`）

对通过前三道闸门的候选，发起**独立调用**。

**关键设计：不得告知模型问题类别，也不得告知哪一个是原文。**

把 `category: A2` 连同原文一起交给模型，等于告诉它"这里有个错，你确认一下"——这是锚定，模型的确认率会被显著抬高。但反过来问"这段文字是否存在需要修改的问题"又是开放题，在中等模型上会持续发现新问题（违反 §12 第 5 条）。两难的解法是**盲测 A/B**：

```
以下两种表述，哪一种存在明确的语言错误？

A. <原文 或 建议文本，随机位置>
B. <另一个>

上下文（仅供理解）：<前后各一段>

只回答：A / B / 两者都没有 / 两者都有
```

判定：

| 模型回答 | 结果 |
|---|---|
| 选中**原文**所在项 | **通过** |
| 选中**建议文本**所在项 | 淘汰（建议反而更差） |
| 两者都没有 | 淘汰 |
| 两者都有 | 淘汰（模型未能区分，视为不可靠） |

这一设计同时达成三件事：消除锚定（模型不知道哪个被质疑）、保持封闭选择题（符合中等模型约束）、**顺带验证 `suggested_text` 确实优于原文**——原设计完全没有验证这一点。

**必须实现 A/B 位置随机化**：LLM 在成对比较中的位置偏好是已知问题，固定顺序会引入新的系统性偏差。随机种子记入 manifest 以保证可复现。

**无 `suggested_text` 的条目**（B 类、逻辑冲突）无法做 A/B，退化为封闭单问：「此处的 <指代/歧义/结构> 是否会导致读者产生两种以上理解？只回答 YES / NO / UNSURE」，**UNSURE 一律按 NO 处理**。

一次调用可批量处理 ≤10 组，降低成本。

**触发范围**（受 `report_threshold` 控制）：

| strictness | 启用类别 | 二次复核 | 说明 |
|---|---|---|---|
| `conservative` | A | 全部 A 类 | 高精准 |
| `balanced`（默认） | A + B | 全部 A + B 类 | 默认取向 |
| `thorough` | A + B + C | A + B（C 类跳过） | C 类只进报告 |

**落笔门槛固定**：只有 `A 类 + 有 suggested_text + 通过编辑距离 + 二次复核 YES` 才生成修订。等价于 `apply_threshold = conservative`，不可配置放宽。

## 9. 逻辑性审查：术语表、台账与冲突规则

### 9.1 术语表来源分层与合并

术语表有三个来源，**合并为唯一出口 `glossary.merged.json`，下游只消费 merged，不感知来源**。这是兼容性的核心：用户提供或不提供外部术语表，Pass 1/2/3 的实现完全不变。

| 层 | 来源 | 优先级 | 默认 `enforce` | 作用 |
|---|---|---|---|---|
| `authoritative` | 用户提供的权威术语表 | 1（最高） | `error` | 既是参照物，**也是规则来源**；违反可生成修订 |
| `extracted` | Pass 0 自动抽取 | 2 | `warn` | 报告 + 批注 |
| `fallback` | 用户提供的兜底术语 | 3（最低） | `off` | **只作参照物**，用于抑制误报，不主动报问题 |

**兜底层的价值在于 `off`**：它不产生任何问题，只是告诉模型"这是合法术语，别改它"，是纯粹的误报抑制资产（供闸门 N7 消费），与高优先级层的作用方向相反。

外部术语表是**可选输入**——Pass 0 的自动抽取在任何情况下都必须执行，外部表只改变其行为，不替代它。

#### 9.1.1 统一内部格式

```json
{
  "entries": [{
    "key": "边缘节点",
    "preferred": "边缘节点",
    "variants": ["边缘结点", "edge node", "EN"],
    "forbidden": [{"form": "边沿节点", "reason": "错别字"}],
    "definition": "……",
    "source": "authoritative|extracted|fallback",
    "priority": 1,
    "scope": "global|<章节路径>",
    "case_sensitive": false,
    "enforce": "error|warn|off"
  }]
}
```

#### 9.1.2 导入与合并

- `scripts/import_glossary.py` 支持 **CSV / XLSX / YAML / JSON / 纯文本（一行一词）** 五种输入——用户手上最可能是 Excel 导出的表，不得强制其转换格式。
- 归一化键：去空白、全半角统一、大小写按 `case_sensitive` 处理。
- **导入期自检**：层内重复、跨层定义矛盾（同一 key 在 authoritative 与 fallback 中定义冲突）→ **报错终止，不做猜测性合并**。用户的表自身有矛盾，必须由用户解决。
- 合并规则：按归一化键聚合，高优先级层覆盖低优先级层的 `preferred` / `definition`；`variants` 取并集；`forbidden` 取并集。
- fallback 层产生的任何问题，严重度自动降一级，且默认不进文档。

#### 9.1.3 概念族聚类（只作建议，不作判据）

文档中"AI助手 / 智能助手 / 研发助手 / AI Agent / 智能体"可能是一个概念族的多种写法，也可能是几个不同的东西。**自动聚类本身是高误报源**——聚错了会让 L04/L05 批量误报。

因此：

- Pass 0 用脚本做**候选聚类**：编辑距离 + 拼音相似 + 英文缩写展开匹配 + 共现窗口统计。
- 聚类结果写入 glossary entry 的 `cluster_id` 与 `cluster_confirmed: false`，**不新增文件**。
- `cluster_confirmed: false` 的族**不触发任何 L 规则**，只输出到报告的「待确认概念族」一节。
- 用户确认后可导入 `authoritative` 层，此时 `cluster_confirmed: true`，L04/L05/L26 才对该族生效。

这与 fallback 层的迭代路径一致：**第一轮跑出建议 → 人工确认 → 第二轮才产生判定力**。不要试图让系统自动获得判定力。

#### 9.1.4 Pass 0 的脚本预筛（性能关键）

**不得让 LLM 通读全文来抽术语。** 2000 页全文过一遍 LLM 约需 60 次调用，而术语抽取的信息密度极低。

正确做法是脚本先做候选筛选：

1. 分词 + 词频统计，取高频未登录词、高频名词短语；
2. 缩略语正则（连续大写字母、字母+数字组合）；
3. 定义句式正则（"X 是指"、"X（以下简称 Y）"、"所谓 X"、"X 定义为"）；
4. 标题中出现的名词短语（章节标题往往就是核心术语）。

**只把候选术语所在段落及其前后各一段**交给 LLM 确认定义与别名。2000 页文档的候选术语通常在 200–500 个量级，聚合后约 10 次调用即可完成，较全文扫描节省约 50 分钟。

未被预筛捕获的低频术语会漏掉——这是可接受的：低频术语很少产生跨章节冲突，且用户可通过 `authoritative` 层补充。

#### 9.1.5 对 Pass 0 的影响

外部表存在时，Pass 0 抽取行为调整（顺带降低 token 消耗）：

- 已在 `authoritative` 中登记的术语：**跳过定义推断**，只记录出现位置与实际写法。
- 未登记的术语：正常抽取。
- 抽取产物仍写入 `extracted` 层，与外部表在合并阶段汇合，不在抽取阶段混合。

#### 9.1.6 缓存与重跑代价（架构硬约束）

> **Pass 1 的事实抽取阶段不得做任何术语归一化，必须原样记录 `variants_seen`。**

台账记录的是"文档里实际怎么写的"，术语判定发生在 Pass 3。这条解耦决定了后续补充术语表的代价：

| 变更 | 需重跑 | 成本 |
|---|---|---|
| 补充/修改外部术语表 | **仅 Pass 3 + Pass 4** | 脚本 + 少量 LLM 调用，数分钟 |
| 若在 Pass 1 就归一化（错误设计） | Pass 1 全量 | 占总成本 90%，数小时 |

`glossary.merged.json` 按 `hash(外部表内容 + Pass 0 产物 + 合并规则版本)` 缓存；哈希变化时使 Pass 3/4 产物失效，**但不触碰 Pass 1 产物**。

### 9.2 台账 schema（Pass 1 抽取，`facts-<chunk>.json`）

抽取任务对模型的要求是"照抄+归类"，**不是判断**。schema 固定，字段缺失填 `null`，不允许自由发挥。

**三条硬约束**：

1. **不得做术语归一化**（见 9.1.6），`variants_seen` 必须记录文档中的实际写法。
2. **`serves_objective` 只在文档显式写明对应关系时填写**（如"为实现目标 O1，开展…"）；模型不得自行推断归属。推断出的对应关系会让 L29 的覆盖性检查失去意义——它会把"漏抽"伪装成"已覆盖"。宁可留 `null`。
3. **表格必须抽取**。规划类、可研类文档的关键数字（预算、指标、里程碑、资源投入）绝大多数在表格中，`metrics` 的主要来源是表格而非正文。表格虽跳过语病审查（`tables_language_check`），但**事实抽取不得跳过**，且需标记 `source: "表格"` 以便冲突裁定时区分——表格中的简写与正文表述不一致往往是正常的，而数值不一致则是真冲突。超长表格独立成片时，必须在片头注入该表所属的章节路径与表标题，否则抽取出的指标缺少 `scope`，将无法参与比对。

```json
{
  "terms":      [{"term":"边缘节点","definition":"……","pid":"p-000121","is_definition":true}],
  "acronyms":   [{"acronym":"MEC","expansion":"多接入边缘计算","pid":"p-000121","first_use":true}],
  "entities":   [{"name":"星云平台","variants_seen":["星云","Nebula"],"pid":"p-000305"}],
  "metrics":    [{"subject":"端到端时延","value":"200","unit":"ms","qualifier":"≤","scope":"核心链路","kind":"目标|实测|预期|基线|行业参考","source":"正文|表格","pid":"p-000418"}],
  "positions":  [{"subject":"服务架构","stance":"微服务","pid":"p-000210"}],
  "objectives": [{"obj_id":"O1","statement":"实现研发效率提升","pid":"p-000188"}],
  "initiatives":[{"init_id":"I1","statement":"建设统一代码平台","serves_objective":"O1|null","pid":"p-000260"}],
  "acceptance": [{"target":"I1|O1","criterion":"平台接入率≥80%","pid":"p-000271"}],
  "dates":      [{"event":"一期上线","value":"2026-03","pid":"p-000502"}],
  "versions":   [{"subject":"星云平台","value":"v2.3","pid":"p-000511"}],
  "roles":      [{"role":"数据owner","duty":"审批数据出域申请","pid":"p-000733"}],
  "xrefs":      [{"type":"section|figure|table|appendix","target":"3.2.1","pid":"p-000640"}],
  "numbering":  [{"type":"figure|table","label":"图 3-7","caption":"……","pid":"p-000651"}],
  "commitments":[{"subject":"灰度发布","modality":"必须|将|不低于","statement":"……","pid":"p-000812"}],
  "statuses":   [{"subject":"多租户隔离","status":"已完成|建设中|规划中|不支持","pid":"p-000903"}],
  "enumerations":[{"claim":"三个方面","count_declared":3,"count_listed":4,"pid":"p-001002"}],
  "conclusions":[{"scope":"3.2 数据层","statement":"……","pid":"p-000455"}]
}
```

### 9.3 台账索引化

Pass 3 不得将全量 facts 一次性载入内存。3000 页文档的台账条目可达 20 万条，且 L06 类"同 subject 不同 value"的朴素实现是 O(n²)。

**方案**：`ledger.py` 将各分片的 `facts-*.json` 导入 SQLite（`work/ledger.db`），按 `subject` / `key` / `type` / `pid` 建索引，规则以 `GROUP BY` + `HAVING` 表达。

三项收益：查询复杂度降到 O(n log n)；补充术语表后可只重算受影响的规则；事务天然原子，利于断点续跑。

**硬约束：JSONL/JSON 是权威源，SQLite 只是可随时重建的派生索引。** `ledger.py rebuild` 必须能从 facts 文件全量重建，且重建结果幂等。SQLite 损坏时删库重建，绝不能成为单点。这也与 `require_local_fs: true` 一致——SQLite 在 NFS/SMB 上的锁机制不可靠。

### 9.4 冲突检测规则表（`detect_conflicts.py`，纯脚本）

| ID | 规则 | 严重度 | 动作 |
|---|---|---|---|
| **术语与命名** ||||
| L01 | 同一 `term` 出现 ≥2 个实质不同的 `definition` | High | 批注 |
| L02 | 同一 `acronym` 有 ≥2 个不同 `expansion` | High | 批注 |
| L03 | `acronym` 首次出现处未给出 `expansion` | Low | 批注 |
| L04 | 同一 `entity` 存在多种写法且未登记为别名组（编辑距离/拼音相近） | Medium | 批注 |
| L05 | 近义术语混用指代同一概念（依据 glossary 聚类） | Low | 报告 |
| **数值与量纲** ||||
| L06 | 同一 `(subject, scope)` 出现不同 `value` | **Critical** | 批注 |
| L07 | 同一 `subject` 的 `unit` 不一致（ms/s、GB/G） | High | 批注 |
| L08 | 区间矛盾（min > max、上限 < 下限） | **Critical** | 批注 |
| L09 | 百分比构成合计 ≠ 100%（容差 ±0.5%） | High | 批注 |
| L10 | `enumerations` 中 `count_declared ≠ count_listed` | High | 修订*或批注 |
| L11 | 数值与文字描述不符（"翻倍"但前后值非 2 倍关系） | Medium | 批注 |
| **时间与版本** ||||
| L12 | 同一 `event` 出现不同 `date` | **Critical** | 批注 |
| L13 | 时序倒置（阶段 N 的日期早于阶段 N-1） | High | 批注 |
| L14 | 同一 `subject` 的 `version` 出现倒退或不一致 | High | 批注 |
| **引用与编号** ||||
| L15 | `xref` 指向不存在的章节/图/表/附录 | High | 批注 |
| L16 | 图/表编号跳号或重号 | Medium | 批注 |
| L17 | 目录条目与正文标题文本不一致 | Medium | 批注 |
| L18 | 图/表存在但正文中无任何引用 | Low | 报告 |
| **结构与论断** ||||
| L19 | 章节层级跳级（H2 直接跳 H4） | Low | 报告 |
| L20 | 同一 `subject` 的 `status` 前后矛盾（"不支持" vs "已支持"） | **Critical** | 批注 |
| L21 | 同一 `commitment subject` 的 `modality` 强度冲突（"必须" vs "可选"） | High | 批注 |
| L22 | 同一职责分配给不同 `role`，或同一 `role` 职责表述冲突 | High | 批注 |
| L23 | `conclusion` 与其 scope 内的 `metrics/statuses` 矛盾 | High | 批注 |
| L24 | "综上所述/如上所述"总结的条目数与前文列举不符 | Medium | 批注 |
| **术语规范**（仅在存在 `authoritative` 层时激活） ||||
| L25 | 使用了 `forbidden` 中登记的写法 | High | **修订** |
| L26 | 使用了 `variants` 而非 `preferred` 形式，且 `enforce=error` | Medium | **修订** |
| **立场与论证覆盖性**（面向规划/可研/评审类文档） ||||
| L27 | 同一 `subject` 在 `kind=目标` 与 `kind=实测` 下数值差异超过 `gap_ratio`（默认 3 倍） | High | 批注 |
| L28 | 同一 `subject` 的 `positions.stance` 前后不一致（微服务 vs 单体） | High | 批注 |
| L29 | `objectives` 中的目标无任何 `initiatives.serves_objective` 指向 | Medium | **仅报告** |
| L30 | `initiatives` 中的举措无任何 `acceptance` 关联 | Medium | **仅报告** |
| L31 | `commitments` 中的量化承诺全文无对应度量方式或验证描述 | Medium | **仅报告** |
| L32 | 章节标题承诺的内容在正文中缺失（如"风险分析"下无任何风险条目） | Low | **仅报告** |

\* L10 若能唯一确定正确数字（如列举项数明确为 4），可生成修订；否则批注。

**L29–L32 是覆盖性检查（集合差集），不是论证强度判断**——这是它们能进入 v1 的原因。但它们**依赖抽取完整性**：漏抽一条举措就会误报"目标无对应举措"。因此严重度上限 Medium，措辞统一为「未检索到与 X 对应的 Y，请确认」，**默认只进报告不进批注**（`coverage_rules_to_comment: false` 可开启）。首轮跑完应人工核对其误报率，再决定是否提升其地位。

**L25/L26 是外部术语表带来的最大收益**：命名不一致原本只能出批注（模型无法判断以哪个写法为准），有了权威表之后正确形式唯一确定，因而可以生成修订。这两条同样受 §8 闸门约束——编辑距离检查与二次复核照常执行。

**所有 L 规则的输出都是"候选"，必须过 Pass 4 裁定。**

### 9.5 Pass 4 裁定 prompt 要点

**裁定结果的准入策略是 fail-closed 的**：`CONFLICT` 进交付物；`NOT_CONFLICT` 丢弃；
`UNSURE` 按 `NOT_CONFLICT` 处理，仅 Critical 级保留并标注"需人工确认"；
**没有裁定结果的候选一律不进交付物，Critical 也没有例外**——
未裁定说明流程没走完，与"模型拿不准"是两回事。
该策略由 `_common.py` 的 `conflict_admitted()` 统一实现，
`apply_comments` / `apply_revisions` / `report` 三处共用，不得各写一份。
未准入的候选**不得静默消失**：报告与 `issues.xlsx` 照常列出，并在
「本次未覆盖范围」按原因给出计数。


- 同时给出冲突双方的 `original_text` + 各自的 `heading_path`。
- 唯一问题：「这两处描述是否构成真实矛盾？还是因适用范围/前提条件不同而并不矛盾？回答 CONFLICT / NOT_CONFLICT / UNSURE，并用一句话（≤30 字）说明范围差异。」
- **UNSURE 按 NOT_CONFLICT 处理**（除 Critical 级，Critical 级 UNSURE 保留并标注"待人工确认"）。
- 严禁要求模型判断"哪一处是对的"——它无法知道，这类判断必然是幻觉源。批注文案统一为：「本处与 §X.Y（第 N 页）的描述存在冲突：此处为 A，彼处为 B。请确认以哪一处为准。」

### 9.6 论证链审查（`argument_review`，默认 `off`，v2）

**本节内容不属于 v1 交付范围，仅作接口预留，实现方在 v1 阶段只需保证开关存在且默认关闭、关闭时零开销。**

覆盖 L29–L32 之外的、无法脚本化的判断：证据充分性、结论强度是否超过证据、绝对化表达。

**为什么默认关闭**：这类判断无客观阈值。技术报告的概述、章节引言、小结中大量存在"本方案可有效支撑…""该架构具备良好扩展性"这类表述，其中绝大多数**本就不需要就地给出证据**（证据在后文，或属于领域共识）。模型无法区分"此处应有证据"与"此处是引言"。3000 页文档中这类句子可达数千，即使 10% 误报也是数百条噪音。

**更关键的是误报不可收敛**：其他类别的误报可通过 never-flag 清单逐条压制（有限可枚举），但无法写出一份《哪些论断不需要证据》的清单。这意味着该模块不会随迭代改善，而 spec 中其他模块都会。

若启用，强制约束：

- 只对 `heading_path` 深度 ≥2 且非引言/概述/小结类章节的段落生效（用标题关键词表排除）。
- 只处理带量化表述的论断（`metrics` 中 `kind=目标|预期` 且无对应 `kind=实测|基线` 的条目），不处理定性论断。
- **产出永远只进报告，不进批注、不进修订**，且单独成章，不与其他问题混排。
- 单文档上限 `argument_review_max_issues`（默认 50），超出截断。

启用前应先跑完至少一轮 v1，用真实的问题分布判断该模块是否值得开启。

### 9.7 错别字独立通道（M8）

**为什么必须独立**：错别字是唯一一个**存在确定性候选生成手段**的类别，让 LLM 扫描它先天不利：

1. **LLM 对错别字有鲁棒性，这恰是缺陷。** 模型读到"帐号""布署""按装"会自动理解为正确词，注意力不会停留——它在做语义理解，不是逐字比对。
2. **配额挤占。** 一片 20 页文档可能有 20–40 个错别字，`max_issues_per_chunk: 20` 瞬间打满，且截断按 severity 排序，A1 会被 Critical 级挤掉。
3. **重要性排挤。** 模型倾向报告"看起来更重要"的问题，错别字最不起眼。

**设计（与 D1 同构）**：

```
脚本扫描 → 候选（位置 + 原字 + 候选正字 + 触发规则）
    ↓
LLM 批量裁定（封闭选择题，一次 ≤50 个）
    ↓
过闸门② ③ → 修订
```

**脚本侧**（`scripts/typo_scan.py`，内嵌资源，无网络）：

| 手段 | 资源 |
|---|---|
| 形近字对 | `assets/dict/confusion-shape.txt` |
| 音近字对 | `assets/dict/confusion-pinyin.txt` |
| 常见错词表 | `assets/dict/common-typos.txt`（布署/部署、按装/安装、帐号/账号、既使/即使） |
| 未登录词检测 | `assets/dict/common-words.txt` + 分词 |
| 术语错写 | `glossary.merged.json` 的 `forbidden` + 编辑距离 ≤2 |

资源总体积数 MB，与自闭环要求一致。

**LLM 侧**：任务退化为"两个字选一个"——「此处应为『帐号』还是『账号』？只回答 A / B / 都不对」。中等模型在此类封闭选择上的准确率显著高于自主发现错误，且单条输出仅一个字母，一次调用可处理 50 个候选。**成本极低。**

**配套约束**：

- 错别字**独立计数**，另设 `max_typos_per_chunk`（默认 100），不占用 `max_issues_per_chunk` 的 20 条配额。
- 必须配白名单（"帐篷"不应被改为"账篷"），白名单与 never-flag 同属可枚举、可收敛的资产。
- 混淆集方法误报率高，因此 **LLM 裁定不可省略**，脚本候选不得直接生成修订。

**未登录词检测的取舍（v1.1 决定不做）**：切词后查不到的词即可疑，这条路能突破
「错词对表只查已知错误」的天花板，但需 5 万词级词表才有信噪比。内置词表远未达到该规模，
因此 `typo_check.oov_detection` 默认 `false`，单字混淆集也不参与候选生成——
**错别字召回率的上限就是 `common-typos.txt` 的覆盖范围**。
扩表是提升召回的唯一杠杆，也是可枚举、可收敛的资产；
**不得通过放宽闸门②的 A1 阈值来提召回**，那会把 A1 变成任意改写的入口。

### 9.8 场景描述范式（P 类，`pattern_review`，默认 `off`）

回答一类跟 A/B/L 都不同的问题：**这段文字属于某个已知场景，
而该场景要求写清的几件事，有没有写。** 判据来自**外部规则包**，不来自语言学。

**规则包外置是硬性要求，不是实现便利。** 范式是场景特定的、会持续增加的；
把规则写进代码意味着每加一条就要改类别枚举、闸门与 prompt 三处。
规则因此写在 YAML 里（`assets/patterns/*.yaml` 与用户的 `--patterns`），
**加规则不改代码**。格式与红线见 `references/patterns.md`。

三段式与 D1、错别字通道同构：

```
scan_patterns.py scan   脚本按规则的 scope 确定性定位适用段落（不问模型）
      ↓
LLM 逐要件封闭判定       「『影响』这一要件出现了吗？只答 Y / N / U」
      ↓
scan_patterns.py merge  只有明确 N 成条目；U 按齐备处理（不确定即无问题）
      ↓
闸门②③
```

**约束**：

- `category` 固定为 `P1`（封闭枚举不变），具体范式由 `rule_id` 承载（开放集合，来自规则包）。
- **永不生成 `suggested_text`**。规则包里写了会被拒绝加载；即使漏网，
  闸门②的默认分支也会清空它。要件缺什么内容只有作者知道。
- 严重度上限 `Medium`（`severity_cap`）——与 L29–L32 同理，判定依赖场景定位的准确性。
- 独立配额 `max_pattern_issues_per_chunk`（默认 20），不占用 `max_issues_per_chunk`。
- 表格与代码段不参与（由闸门③ N9/N11 统一处理，`scan` 阶段即排除）。

**与 §9.6 论证链审查的边界**：§9.6 关闭 `argument_review` 的理由是误报不可收敛——
写不出一份《哪些论断不需要证据》的清单。范式审查能进 v1.1 的**唯一原因**是
它的要件清单由规则包给出、是闭合的：场景不命中就不判，命中就只查清单上那几项。
**任何一条 `requires`，如果无法用「这个信息出现了吗」来问，就不该进规则包**——
一旦某条要件变成"这段写得够不够充分"，P 类就退化成了论证链审查。

## 10. 输出物规格

### 10.1 `reviewed.docx`

- 全部修订以统一 author 写入，author 名可配置，默认 `内容审查`。
- 批注按 severity 加前缀：`[严重]` / `[重要]` / `[提示]`。
- 若修订总数 > `max_revisions`（默认 2000），超出部分自动降级为批注，并在报告首页警告。原因：超大量修订会导致 Word 打开缓慢甚至无响应。

### 10.2 `report.md`

固定章节：
1. **执行摘要**：文档规模、耗时、各类问题计数、置信策略说明、被截断/降级的项数。
2. **必须人工确认项**：所有 Critical 级逻辑冲突，按章节排序，附双方原文与页码。
3. **分类统计**：按 A/B/C 与 L 规则的计数表。
4. **按章节明细**：以 `heading_path` 组织。
5. **术语表覆盖率**：外部表中有多少术语在文档中出现；文档中有多少高频术语未被外部表覆盖（按频次降序列出前 30 个，供用户补充到权威表）。
6. **本次未覆盖范围**：明确列出跳过的内容（代码块 N 处、表格 N 个、超长片 N 个）与原因。
7. **参数快照**：strictness、分片参数、术语表来源与条目数、模型标识、运行时间。

### 10.3 `issues.xlsx`

一行一条，列：`id | 严重度 | priority_score | 类别 | 规则ID | 章节路径 | 页码 | 原文 | 建议 | 动作 | 复核结果 | 记忆命中 | 人工决策 | 备注`。

- `priority_score` 由脚本计算，**仅用于排序展示**，不参与任何判定（见 D2）。
- `人工决策` 为空列，供评审人填写 `accept/ignore` 并通过 `import_decisions.py` 回灌审查记忆（§11.7）。

用于人工批量筛选与线下评审。

### 10.4 `glossary.json`

Pass 0 自建的术语表作为**独立可复用产物**输出。用户人工修订后可作为下次运行的输入（`--glossary` 参数），此时误报率会显著下降。**在报告结尾明确提示这一点**——这是从"无参照物"走向"有参照物"的唯一路径。

### 10.5 `metrics.json`（调优的唯一依据，非可选）

核心质量指标是「负样本误报率 ≤5%」，而调整 prompt 的唯一依据是各闸门的丢弃率。**没有这份数据，调优是盲的。** 因此它是 M2 的必需品，不是运维锦上添花。

```json
{
  "llm_calls": {"pass0":12,"pass1_review":186,"pass1_extract":186,"pass2_verify":47,"pass4":23},
  "tokens": {"input":4210000,"output":382000},
  "gates": {
    "raw_candidates": 1842,
    "hallucination_drop": 96,
    "neverflag_drop": 411,
    "edit_gate_drop": 133,
    "second_pass_drop": 289,
    "truncated_chunks": 4,
    "final_issues": 913
  },
  "actions": {"revision":221,"comment":609,"report_only":83},
  "retries": {"json_parse":11,"chunk_failed":2,"chunk_skipped":0},
  "timing": {"total_sec":14820,"avg_chunk_sec":63,"pass3_sec":214}
}
```

`gates` 四个丢弃数直接告诉你哪道闸门在起作用、哪道形同虚设。若 `neverflag_drop` 接近 0，说明不改清单没写对；若 `second_pass_drop` 超过 50%，说明第一遍审查过于宽松。

### 10.6 版本标识

`report.md`、`issues.xlsx`、`glossary.merged.json`、`metrics.json`、`manifest.json` 全部在头部写入：

```yaml
spec_version: "1.1"        # 本规格版本
schema_version: "3"        # 数据结构版本，字段增删时递增
skill_version: "1.1.0"     # 技能实现版本
runid: "run-20260802-1530-a82b"
```

`issues.xlsx` 未来增列（如 `priority_score`）时，下游工具据 `schema_version` 判断兼容性，避免静默错列。

## 11. 工作目录、状态管理与断点续跑

3000 页任务不可能在单次会话内完成，断点续跑是架构前提而非优化项。同一工作目录下会对多个文档反复执行本技能，目录隔离是正确性前提而非整洁性要求。

### 11.1 工作目录解析

按以下优先级解析**输出根目录**，取第一个有效值：

1. 命令行参数 `--output-dir <path>`
2. 环境变量 `DOCX_REVIEW_OUTPUT_DIR`
3. **Agent 当前工作目录（CWD）** ← 默认

解析后必须执行三项校验，任一不通过即终止：

- **不得位于技能目录之内**：将解析结果与技能包根目录做 `realpath` 前缀比较，命中即报错。这是防止产物污染技能目录的最后一道防线。
- **不得位于源文档所在目录**（除非该目录恰好就是 CWD 且用户显式指定）。
- **必须可写**：实际创建一个探针文件并删除，不依赖权限位判断。

### 11.2 按文档隔离的目录布局

```
<输出根目录>/
└── docx-review/
    ├── 系统设计说明书-3f9a2c71b4d8/       ← <文档slug>-<sha12>
    │   ├── latest.json                   ← 指向最近一次 run 的指针文件
    │   ├── owner.json                     ← 独占租约（session_id + generation + 心跳）
    │   ├── glossary.json                  ← 跨 run 复用的术语表（run 之外）
    │   └── run-20260802-1530-a82b/        ← 时间戳 + 4 位随机后缀，避免秒级冲突
    │       ├── manifest.json              ← 派生视图，可由目录扫描重建
    │       ├── config.snapshot.yaml
    │       ├── work/                      ← 中间产物（可清理）
    │       │   ├── source-copy.doc
    │       │   ├── normalized.docx
    │       │   ├── unpacked/
    │       │   ├── paragraphs.jsonl
    │       │   ├── ledger.db              ← 派生索引，可从 facts 全量重建
    │       │   ├── chunks/chunk-0001.txt … + 0001.claim …
    │       │   ├── issues/issues-0001.jsonl …   ← 存在 = 该片已完成
    │       │   ├── facts/facts-0001.json …      ← 存在 = 该片已完成
    │       │   ├── conflicts-candidate.json
    │       │   └── conflicts-verified.jsonl
    │       ├── output/                    ← 交付物（不可清理）
    │       │   ├── 系统设计说明书.reviewed.docx
    │       │   ├── report.md
    │       │   ├── issues.xlsx
    │       │   ├── metrics.json
    │       │   └── glossary.merged.json
    │       └── logs/
    ├── review-memory.json                 ← 跨文档共享，见 §11.7
    └── 年度技术规划-8b1e04d5c2f1/
        └── …
```

**隔离键的构成**：

- `<文档slug>`：源文件名去扩展名，非法字符（`/ \ : * ? " < > |` 与控制字符）替换为 `-`，压缩连续分隔符，截断至 40 字符。仅为人类可读，**不参与匹配**。
- `<sha12>`：源文档 `sha256` 前 12 位（十六进制）。

**前缀长度不解决碰撞，全长校验才解决。** 8 位前缀是 32 bit，生日碰撞在约 7.7 万份文档时即达 50%——企业几年累积很容易触及。但把前缀加长只是推后概率，不是消除。真正的修复是：

> **命中目录后必须比对 `manifest.json` 中存储的完整 `sha256`，不一致则新建目录（追加 `-2`、`-3` 序号后缀）。**

有了全长校验，前缀长度就退化为纯粹的目录可读性问题，不再是正确性问题。默认取 12（`hash_prefix_len: 12`），代价仅 4 个字符。

采用内容哈希而非文件名作为隔离键，同时解决三种串台：

| 场景 | 结果 |
|---|---|
| 两个不同文档恰好同名（`设计说明书.docx`） | sha12 不同 → 两个独立目录，不串台 |
| 同一文档被改名后再次执行 | sha12 相同 → 命中原目录，可续跑 |
| 同一文档被修改后再次执行 | sha12 变化 → 新建目录，旧结果保留，不会被错误续跑 |

**交付物命名必须带原文档名**（`<原文件名>.reviewed.docx`），因为用户很可能把多个文档的产物拷到一起。

### 11.3 并发控制（同一文档被多会话执行）

**前提认知**：在 Agent 运行时中，每次脚本调用都是独立的短命进程。**基于 pid 存活的锁检测不成立**——写锁的进程在下一次调用前就已退出，第二个会话会把有效锁误判为陈旧锁。锁的活性判据必须是**租约心跳**，不是进程存在。

**设计取向**：不一刀切拒绝。Pass 1/2 占整体耗时 90% 以上且天然一片一文件，多会话同时处理同一文档在该阶段是可利用的并行度而非冲突。

#### 11.3.1 阶段并发属性

| 阶段 | 共享写目标 | 并发属性 |
|---|---|---|
| Pass -1 初始化 | 目录、锁 | 独占（极短） |
| Pass 0 术语台账 | `glossary.json` | **独占** |
| Pass 1 分片审查 | `issues/issues-NNNN.jsonl` | **可并行**（分片 claim） |
| Pass 2 复核 | 同上 | **可并行**（分片 claim） |
| Pass 3 冲突检测 | `conflicts-candidate.json` | **独占** |
| Pass 4 裁定 | `conflicts-verified.json` | **独占** |
| 回写 + 报告 | `output/*` | **严格单写** |

#### 11.3.2 第一层：分片级 claim

- 处理分片 N 前，以 `O_EXCL` 原子创建 `work/chunks/NNNN.claim`，内容 `{session_id, generation, claimed_at, expires_at, _debug:{hostname, agent_version, pid}}`。
  > `_debug` 字段**仅供排障**（例如查明"分片 112 为何一直被 claim"），**严禁参与任何判活或接管逻辑**。§11.3 开头已论证 pid 在 Agent 运行时中不可用于判活；此处保留 pid 却不加约束，实现方极易再次误用。
- 创建成功 → 处理该片；创建失败（已存在）→ 跳过，取下一片。
- claim TTL 默认 `chunk_claim_minutes: 20`。回收过期 claim 前，**必须先检查产物是否已存在**，存在则直接标记完成而非重跑。
- 产物写入成功后删除 claim 文件。
- 所有分片处理完毕即进入独占阶段的等待队列，由**最后一个完成分片的会话**尝试取独占租约推进 Pass 3。

#### 11.3.3 第二层：文件存在性即状态

`manifest.json` 是单一共享可变文件，多会话并发更新必然互相覆盖。因此**取消其权威地位**：

- 分片是否完成，**由 `issues/issues-NNNN.jsonl` 与 `facts/facts-NNNN.json` 是否存在判定**。
- `manifest.json` 降级为派生视图，由 `state.py rebuild` 扫描目录重建，任何会话可随时重建，重建结果幂等。
- **所有产物写入必须走「写 `.tmp` → `os.replace()`」**。半写入的文件绝不能表现为"已完成"。这是本机制成立的必要条件。

#### 11.3.4 第三层：会话令牌栅栏

独占阶段（Pass 0/3/4、回写、报告）由 `owner.json` 保护：

```json
{"session_id":"s-9f2a…","generation":17,"runid":"run-20260802-1530-a82b","acquired_at":"…","last_heartbeat":"…","expires_at":"…","stage":"pass3"}
```

- **`generation`（纪元）单调递增，每次接管 +1。** `session_id` 只能判断"不匹配"，`generation` 能判断**先后**——旧会话可以明确知道"我持有 gen 16，当前已是 gen 17，我被接管了"，日志与用户提示因此可读。这是 ZooKeeper / etcd / Kubernetes Lease 的通行做法。
- 每次脚本调用续租（更新 `last_heartbeat` / `expires_at`），TTL 默认 `lease_minutes: 30`。**续租本身必须原子**：写 `.tmp` → `os.replace()`，且写入前校验 `(session_id, generation)` 匹配，不匹配则拒绝续租而非覆盖。
- 所有独占阶段脚本接收 `--session <id> --generation <n>`，写入前与 `owner.json` 比对；**任一不匹配即以退出码 9（NOT_OWNER）拒绝写入**，不做任何降级、不重试。
- 租约可能因超时被误判而被他人接管，但栅栏不会失效：被接管的旧会话即使恢复活动，其令牌已作废，无法写入。**租约管调度，令牌管安全。**
- 回写 `.reviewed.docx` 前必须再校验一次令牌，然后 `写 .tmp → os.replace()`。

#### 11.3.5 加入的前置条件

第二个会话请求 [1] 加入协作时，必须同时满足，否则只能选 [3] 独立重跑：

1. `config.snapshot.yaml` 哈希一致（`balanced` 与 `thorough` 的产物混在一个 run 内无意义）。
2. 技能版本一致。
3. 工作目录位于**本地文件系统**——`O_EXCL` 在 NFS/SMB 上的原子性不可靠。检测到网络文件系统时**关闭协作模式，退化为 fail-closed**：直接拒绝第二个会话并说明原因。
4. `paragraphs.jsonl` 与分片结果已存在（Pass 0 已完成）。Pass 0 尚未完成时无可分工内容，只能等待或另起。

#### 11.3.6 用户交互（选项集随阶段变化）

检测到活跃租约时**禁止静默失败或静默接管**，必须呈现现状并让用户决策。**可选项由持有租约方所处阶段决定，不是固定三项**：

| A 所处阶段 | B 可选项 | 说明 |
|---|---|---|
| Pass 0 | 等待 / 独立重跑 | 尚无分片，无可分工内容 |
| Pass 1–2 | **加入协作** / 接管 / 独立重跑 | 唯一提供协作的阶段 |
| Pass 3–4 | 等待并轮询 / 接管 / 独立重跑 | 分片已尽，协作无意义 |
| 回写中 | 等待 / 独立重跑 | **不提供接管** |

**回写阶段禁止接管**是硬规则：该阶段写的是最终交付物，租约误判叠加接管的代价最高，而等待成本最低（通常数分钟）。即使租约已过期，回写阶段也只允许在用户显式确认"原任务确已终止"后，走「独立重跑」路径。

Pass 1–2 阶段的交互示例：

```
检测到该文档已有一个进行中的审查任务：
  运行 ID   run-20260802-1530
  当前阶段  分片审查（Pass 1）
  已完成    142 / 186 片
  最后活动  3 分钟前

  [1] 加入协作 —— 与已有任务分工处理剩余 44 片（推荐）
  [2] 接管    —— 已有任务视为中断，由本会话继续（原会话将无法写入）
  [3] 独立重跑 —— 新建 run，不影响已有结果
```

「最后活动」必须显示真实间隔，这是用户判断"另一个会话是否还活着"的唯一依据，不得由程序代为推断。选择 [2] 时立即轮换 `session_id` 使旧令牌作废。

#### 11.3.7 独占阶段的租约保活与接管保护

独占阶段是租约机制最脆弱的地方——长操作期间缺少自然的心跳点，TTL 可能在操作尚未完成时到期，导致存活的会话被误判为死亡。三项保护缺一不可：

**(a) 长操作必须保活**

| 操作 | 保活方式 |
|---|---|
| Pass 3 冲突检测（全量台账两两比对，可达数分钟） | 脚本内开**后台心跳线程**，操作期间持续续租，结束即终止 |
| 回写 docx（数十 MB XML 上千处插入） | 同上 |
| Pass 4 裁定（LLM 调用，脚本不在运行） | Agent **必须在每次 LLM 调用前后显式执行 `state.py heartbeat --session <id>`** |

**(b) 独占阶段本身必须可断点**

这比 (a) 更根本：**它让租约误判从灾难降级为几秒钟的损失。**

- Pass 4 裁定结果以 **append-only JSONL** 逐条落盘（`conflicts-verified.jsonl`），每条含 `conflict_id`；重启时读取已完成的 `conflict_id` 集合，只处理剩余项。
- Pass 3 按规则分组落盘（`conflicts-candidate.L06.json` 等），已完成的规则不重算。
- 回写按"先生成完整补丁清单 → 一次性应用"两段式：补丁清单可断点重建，应用阶段短且原子。

**(c) 消除 TOCTOU 窗口**

"校验令牌 → 写入"之间存在时间窗。解法是**独占阶段的产物路径一律带 session 后缀**：

```
work/conflicts-verified.s-9f2a.jsonl     ← 各会话各写各的
output/系统设计说明书.reviewed.s-9f2a.docx
```

完成后由持令牌者执行 `os.replace()` 原子改名为正式名。改名前再校验一次令牌。两个会话即便真的并发，也只是各写各的临时文件，只有一个能成为正式版本，绝不会出现产物撕裂或互相覆盖。

**(d) 被拒写时的用户提示**

退出码 9（NOT_OWNER）不得直接暴露给用户。Agent 必须转译为可理解的说明，并给出后续动作建议：

```
本会话的写入权限已失效——该文档的审查任务已被另一个会话接管
（接管时间 14:22）。本会话已完成的分片结果仍然有效并已保留。
建议：切换到另一个会话查看进度，或选择「独立重跑」。
```

**不同文档之间无任何竞争**——这是按内容哈希隔离带来的收益，用户可在同一工作目录下自由并行处理多个文档。

### 11.4 清理策略

- `work/` 默认保留（续跑依赖），提供 `--clean-intermediate` 在成功完成后删除。
- 每个文档目录下最多保留 `keep_runs`（默认 3）个 run，超出按时间淘汰最旧的，**但从不自动删除 `output/`**。
- `glossary.json` 提升到文档目录层级，跨 run 复用；每个 run 的 `output/` 内另存一份快照。

### 11.5 状态文件

`manifest.json`：

```json
{
  "spec_version":"1.1",
  "schema_version":"3",
  "runid":"run-20260802-1530-a82b",
  "source":"/path/原文档.docx",
  "source_sha256":"…",
  "generation":17,
  "stage":"pass1",
  "config":{"strictness":"balanced","max_context_tokens":45000},
  "chunks":[
    {"id":"0001","status":"done","issues":7,"facts":23,"attempts":1,"finished_at":"…"},
    {"id":"0002","status":"failed","attempts":2,"last_error":"json parse error"},
    {"id":"0003","status":"pending"}
  ],
  "stats":{"total_chunks":186,"done":142,"failed":2,"pending":42}
}
```

**续跑协议**（写入 SKILL.md 主流程首步）：

1. 启动时先算出当前输入的 `sha12`，**只在 `docx-review/*-<sha12>/` 这一个目录下查找**（不遍历其他文档的目录）；命中后再比对 manifest 中的完整 `sha256`，不一致则视为新文档并新建带序号后缀的目录。若其 `latest.json` 指向的 run 满足 `stage != "completed"` → **询问用户是续跑还是新建**。未命中即视为新文档，直接新建。
2. 续跑时只处理 `status ∈ {pending, failed}` 的分片。
3. `failed` 分片最多重试 3 次；仍失败则标记 `skipped`，并**必须**在最终报告的"未覆盖范围"中列出。
4. 每完成一个分片立即以「写 `.tmp` → `os.replace()`」原子落盘，随后删除该片 claim；`manifest.json` 由 `state.py rebuild` 按需重建，不作为并发写入点。
5. 主 Agent **只读 manifest 的 stats 字段**，不读 chunks 数组全文。

### 11.6 故障恢复矩阵

前文各节隐含覆盖了多数故障，此处集中列出，便于实现方按场景逐项验证。**所有恢复动作必须幂等，且不得触碰源文档。**

| 场景 | 恢复策略 |
|---|---|
| `manifest.json` 丢失或损坏 | `state.py rebuild` 扫描目录重建（它本就是派生视图） |
| `owner.json` 损坏 | 视为无主，`generation` 从 manifest 记录的最大值 +1 重建 |
| `ledger.db` 损坏 | 删库，从 `facts/*.json` 全量重建 |
| `glossary.merged.json` 损坏 | 从三层来源重新合并；外部表不可读则终止并提示 |
| 分片半写（存在 `.tmp`） | 删除 `.tmp` 与对应 claim，该片重回 pending |
| claim 残留但产物已存在 | 删除 claim，标记该片完成，不重跑 |
| claim 残留且产物不存在且已过期 | 回收 claim，该片重回 pending |
| `report.md` / `issues.xlsx` 缺失 | 从 `issues-verified.jsonl` + `conflicts-verified.jsonl` 重生成，无需重跑任何 Pass |
| `reviewed.docx` 损坏或 XSD 校验失败 | 丢弃，从 `normalized.docx` 重新回写；仍失败则只交付报告并明确告警 |
| `output/` 已存在同名交付物 | 不覆盖，追加 `-2` 序号；正式名由持令牌者原子改名产生 |
| 外部术语表被删除或改动 | merged 哈希失配 → 使 Pass 3/4 产物失效，**Pass 1 产物保留**（见 9.1.6） |
| `source-copy` 缺失 | 从源文档重新复制并校验 sha256；源文档也已不可读则终止 |
| doc 转换产物损坏 | 删除后重新转换；重复失败 2 次则终止并提示环境问题 |
| 令牌被作废（退出码 9） | 不重试、不降级；转译为用户可读提示（见 11.3.7d），已完成的分片产物保留 |
| 磁盘写满 | 立即终止，保留已有产物，提示所需空间；**禁止为腾空间自动删除任何产物** |

### 11.7 审查记忆（Review Memory）

误报抑制的长期资产。文档中有一类问题反复出现却每次都被人工驳回——公司写作习惯、行业惯用表述、领域内约定俗成的搭配。这些不是术语，无法进 glossary。

**存储位置：工作目录级（`docx-review/review-memory.json`），跨文档共享。** 放 run 目录会随清理消失，失去全部价值。

```json
{
  "schema_version": "1",
  "entries": [
    {"key_hash":"…","category":"B3","original_norm":"…","decision":"ignore","reason":"公司写作习惯","created_at":"…","hit_count":7}
  ]
}
```

**两条复用路径，不得有第三条**：

1. **精确复用**：键为 `(category, 归一化后的 original_text)` 的哈希。归一化仅限空白与全半角统一，不做任何语义处理。命中即自动降级为 `report_only`。技术报告跨文档大量复用整段模板文字，这条命中率比直觉高。
2. **人工提炼**：用户把某条反复出现的误报提炼为 never-flag 规则或 fallback 术语，写回 `references/` 或外部术语表。

> **严禁让系统从历史决策自动泛化规则。** "用户忽略了 3 条 B3，所以以后 B3 都降级"这类推断会制造新的、更隐蔽的漏报。记忆只能精确匹配，泛化必须经人。

写入时机：用户在 `issues.xlsx` 中标注驳回并回灌（`import_decisions.py`）。**首轮运行时该文件为空是正常状态**，价值从第二个文档开始显现。

## 12. 中等能力模型适配要点

写入 `SKILL.md` 与各 prompt 模板的强制约束：

1. **单一职责**：一次调用只做一件事。审查与抽取**分开两次调用**，不合并（合并会导致两个任务互相污染，且弱模型倾向偏向其中之一）。
2. **输出格式固定为 JSONL**，一行一条，无外层包裹、无 Markdown 代码围栏、无前言后语。解析失败自动重试一次，附上"上次输出无法解析"的提示；二次失败标记该片 failed。
3. **禁止长理由**：`evidence` 字段限 ≤25 字。理由越长模型越容易自我说服，误报率越高。
4. **禁止算术**：所有数值比较、计数、百分比合计、编号连续性由脚本完成，不交给模型。
5. **禁止全局判断**：不问"这个问题重要吗"、"整体逻辑是否通顺"、"文档质量如何"这类开放问题。
6. **反例优先**：`never-flag.md` 中反例数量应 ≥ 正例数量。这是抑制过纠最有效的单一手段。
7. **温度设为 0**（或平台最低值）。
8. **枚举一切**：类别、严重度、动作、复核结论全部是封闭枚举，模型只能选，不能造。
9. **每片强制上限**（默认 20 条）：无上限时模型会持续"发现"问题以显得尽职。
10. **不做多轮对话**：每次调用无状态、自包含，便于重试与并行。

## 13. 项目框架划分与开发效率

### 13.1 SKILL.md 放什么（运行时加载）

- frontmatter：`name` / `description`（触发描述需"主动"，覆盖"审查/校对/查错/通读/一致性/前后矛盾/语病"等表述）/ `platform: XAgent`
- 主流程 5 步（Pass -1 至 Pass 4），每步一段，不展开细节
- **CLI 契约表**：每个脚本的用途、输入、输出、退出码。**Agent 据此调用脚本，无需阅读脚本源码**——这是最大的 token 节省点
- 决策点：单片 vs 分片的判定、strictness 的选取、续跑判定
- 指向 references 的路标：「判定某问题属于哪一类时，读 `references/taxonomy.md`」

**目标 ≤ 400 行。** 超出则再加一层 references。

### 13.2 references 放什么（按需加载）

类型体系、不改清单与反例、逻辑规则表、schema、prompt 模板、OOXML 要点。这些内容体量大但只在特定步骤需要，绝不进 SKILL.md。

### 13.3 CLAUDE.md 放什么（开发期加载，运行时永不加载）

```markdown
# 项目定位与非目标
# 目录地图 —— "要改 X，去改哪个文件" 索引表
# 开发环境与依赖安装
# 编码约定
  - 每个 script 必须：可独立 CLI 调用 / 幂等 / 不联网 / 退出码规范 / 不打印大对象
  - 所有对模型的调用必须走统一封装，便于换模型与打桩测试
  - 新增规则必须同步：taxonomy.md + prompt 模板 + tests/fixtures
# 测试语料位置与回归命令
# 当前进度 → 见 docs/progress.md
# 决策日志 → 见 docs/decisions.md
# 【硬约束】SKILL.md 及 references 不得引用本文件任何内容
```

### 13.4 跨 session 续接开发

- **`docs/progress.md` 是唯一入口**，格式固定：当前阶段 / 已完成模块清单 / 进行中（含未提交的半成品位置）/ 下一步 3 条 / 未决问题。**每次会话结束前必须更新**。
- **`docs/decisions.md` 用 ADR 格式**：编号 / 日期 / 决策 / 备选方案 / 理由 / 影响文件。避免下次会话重复讨论已定事项。
- **省 token 的具体做法**：
  1. 新会话开场只读 `CLAUDE.md` + `docs/progress.md`，**禁止全仓扫描**。
  2. 脚本通过 CLI 契约调用，不读源码。
  3. 用小 fixture（3–5 页）跑快速回归，大语料只在里程碑跑。
  4. 一次会话聚焦一个模块，不跨模块重构。
  5. 长输出（报告、issues）落盘后只回读统计行。

## 14. 关键设计的实证依据

供实现方理解 D2 与 §8 的由来，不必写入技能包：

- **模型自评置信度不可作阈值**：研究发现言语化置信度存在系统性失准，在低准确率样本上仍报出高置信度；同时存在"置信度饱和"——分数集中在少数高分箱，导致不存在既能接受结论又能拒绝大部分错误结论的阈值点。另有研究指出，已作出判断的 Agent 倾向为自身判断辩护而非批判它，因此此类分数只能作排序信号，不能当概率使用。
- **过纠是中文纠错的核心难点**：同一基线模型在中文数据集上的精确率通常只有英文的约一半；LLM 在零样本/少样本设置下同样存在大量过纠。有效缓解手段是基于投票的集成，代价是召回下降——这正是本 spec 采用"二次独立复核 + UNSURE 按否定处理"并接受召回损失的依据。编辑距离对比也证实 LLM 相比人工标注者倾向做更多修改，故设置编辑距离闸门。
- **该领域标准评价指标为 F0.5**（精确率权重高于召回率），与"报告可平衡、落笔必保守"的双门槛取向一致。

## 15. 开发计划与验收标准

### 15.1 里程碑

| M | 内容 | 验收 |
|---|---|---|
| M1 | 工作目录隔离 + 源文档保护 + 环境探测 + 格式转换 + 解包 + 段落抽取 | ① 3 类环境下 doc/docx 均能产出正确 `paragraphs.jsonl`；② 无转换工具时正确终止并给出指引；③ **源文档 sha256 全程不变，且源目录无任何新增文件**；④ **技能目录 mtime 全程不变**；⑤ 同一工作目录下对两个同名不同容的文档先后执行，产物完全隔离且续跑不误命中 |
| M2 | 分片 + Pass 1 审查 + 三道脚本闸门 + 盲测 A/B 复核 + **metrics.json** | ① 5 页 fixture 上 A 类召回 ≥80%，`original_text` 匹配失败率 = 0；② metrics.json 输出四项闸门丢弃率；③ A/B 位置随机化后，两种排列下的判定一致率 ≥90%（低于此说明模型存在强位置偏好，需换 prompt） |
| M3 | Pass 0 术语台账 + 概念族聚类 + 三层术语合并 + Pass 1 事实抽取 + SQLite 索引 + Pass 3 冲突检测 | ① 注入式 fixture（人为埋 32 条 L 规则冲突）检出率 ≥90%；② **补充外部术语表后，仅重跑 Pass 3/4 即可生效，Pass 1 产物零重算**；③ 外部表自身矛盾时正确终止；④ **L29–L32 覆盖性规则在真实文档上人工核对误报率并记录基线**；⑤ 删除 `ledger.db` 后可全量重建且结果一致 |
| M4 | 二次复核 + Pass 4 裁定 | 在含 30 条"合法表达"的负样本集上，误报 ≤2 条 |
| M5 | 修订 + 批注回写 + 校验 | ① `validate_docx.py` 零未追踪变更；② Word 中可逐条接受/拒绝；③ **样式不变性四项检查全部通过（D9）：样式类文件哈希不变、无格式修订标记、rPr 逐 run 一致**；④ 批注增强层（commentsExtended/Ids/Extensible）写入失败时降级为仅核心层，批注仍可见，不整体失败 |

| M7 | 3000 页压测 + 并发调优 | ① 完整跑通，峰值单次上下文占用 <60%，产出可打开；② 确定 `parallelism` 实际最优值并回填 §7.4.3；③ 限流退避期间 claim 不被误回收，无分片重复处理 |
| M8 | 错别字独立通道（§9.7） | ① 在含 100 个已知错别字的 fixture 上召回 ≥85%；② 白名单负样本（帐篷、其它等）零误报；③ 不占用 `max_issues_per_chunk` 配额 |

### 15.2 测试语料（`tests/fixtures/`）

必须准备四类：

1. **正样本**：每个 A/B 类各 ≥3 个真实错例，含期望的 `suggested_text`。
2. **负样本（最重要）**：≥30 条完全合法但容易被误判的表达，覆盖 N1–N14 每一条。**这是衡量本技能是否可用的核心指标。**
3. **逻辑注入样本**：一篇 30–50 页文档，人为埋入 L01–L32 每条至少 1 例，附答案清单。
4. **规划/可研类样本**：一篇含大量表格（预算表、指标表、里程碑表）的规划类文档，用于验证表格事实抽取与 L27–L32。这是本项目的主要目标场景，不可省略。
5. **样式回归样本**：一篇使用多种字体字号（三号仿宋正文、黑体标题、混排西文、带编号列表）的文档，回写后逐 run 比对 `rPr`，验证 D9。
6. **规模样本**：≥500 页真实文档，用于压测与耗时评估，**并记录实测页密度**。

### 15.3 核心验收指标

| 指标 | 目标 |
|---|---|
| 负样本误报率（N 清单） | **≤ 5%** |
| A 类召回率 | ≥ 80% |
| 逻辑冲突（L 规则）检出率 | ≥ 90% |
| 定位准确率（`original_text` 可匹配） | 100%（不可匹配者已被丢弃） |
| 回写后未追踪变更数 | **0** |
| 回写后样式变更数（D9 四项检查） | **0** |
| 源文档被修改次数 | **0**（含异常终止、中断、重试路径） |
| 跨文档产物串台 | **0** |
| 3000 页任务可完成性 | 支持中断续跑，不因单片失败而整体失败 |

**优先级排序：源文档完整性 > 样式不变性 > 定位准确率 > 回写安全性 > 误报率 > 逻辑检出率 > 语病召回率。** 当指标冲突时按此序取舍。前三项是安全底线，任何为提升后四项而放松前三项的方案一律否决。

## 附：给实现方的五条提醒

1. **先建负样本集，再写审查逻辑。** 没有负样本集，无法判断任何一次 prompt 调整是改善还是恶化。这是本项目最容易被跳过、也最致命的一步。
2. **修订回写留到最后做，但批注不是。** 前六个里程碑全部只出报告，确认误报率达标后再打开**修订**。批注是逻辑审查的唯一交付出口，砍掉它等于砍掉逻辑审查——两者风险不对等，不要一起延后。
3. **`metrics.json` 从 M2 就要有。** 你唯一的调优依据是四道闸门各自的丢弃率。没有这份数据，改 prompt 只能靠感觉，而感觉在误报率这件事上一贯不准。
4. **`workspace.py` 是第一个要写的文件，不是最后一个。** 所有其他脚本的文件路径都必须经它解析。等到 M5 才补路径守卫，意味着前面四个里程碑的调试过程中随时可能写坏源文档或污染技能目录，而这类事故往往在很久以后才被发现。
5. **任何"让模型多想一步"的诱惑都要抵制。** 本 spec 的所有设计都指向同一个方向：把判断压缩成分类，把比较交给脚本，把不确定一律当作"无问题"。
